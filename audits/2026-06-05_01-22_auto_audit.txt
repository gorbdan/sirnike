## 🔴 [SirNike.py:2896-2950] Потеря платежа при краше в run_generation между spend и enqueue

**Код:**
```python
if not spend_izyminki(user.id, cost):
    queued_user_ids.discard(user.id)
    await reply_target.reply_text("Не удалось списать изюминки. Попробуй ещё раз.")
    return

paid = True

try:
    _bounded_set(last_generated_prompt, user.id, state.prompt)
    # ... более 20 строк кода с await операциями ...
    generation_queue.put_nowait(job)
```

**Проблема:** 
Между `spend_izyminki()` (строка 2933) и последующим блоком `try` (строка 2940) нет `await`, но внутри `try` есть множество операций, включая валидацию и `await reply_target.reply_text()`. Если случится необработанное исключение **в момент построения job-объекта или логирования** (строка 2943-2956), то:
1. Изюминки уже списаны (`paid = True` уже выставлен)
2. Job не попал в очередь
3. Восстановление в `except BaseException` (строка 2972) пытается вернуть, но может не сработать, если исключение произойдёт между `paid = True` и строкой 2940

**Воспроизведение:** 
Если при выполнении `_bounded_set()` или `get_avatar_urls()` произойдёт исключение (например, ошибка БД), пользователь потеряет изюминки без попадания в очередь.

**Фикс:** 
Переместить `paid = True` внутрь `try`-блока:
```python
try:
    paid = True  # выставить здесь, в зоне except обработки
    _bounded_set(last_generated_prompt, user.id, state.prompt)
    ...
except BaseException as _enqueue_exc:
    if paid:  # теперь безопасно проверить
        add_izyminki(user.id, cost)
```

**Код:**
```python
source_group_items: List[Dict[str, Any]] = []
if source_message and getattr(source_message, "media_group_id", None):
    source_group_items = get_cached_media_group(
```

**Проблема:** 
`source_group_items` содержит `List[Dict[str, Any]]`, которые могут включать большие бинарные данные. При раннем выходе (строка ~1791 `return`) список не очищается и остаётся в памяти до конца функции. За несколько рассылок это может привести к утечке.

## 🔴 [SirNike.py:2372-2450] Race condition в apply_webapp_prompt_payload_v2: PROMPT_LIBRARY может измениться между проверкой и доступом

**Код:**
```python
if not (0 <= cat_idx < len(PROMPT_LIBRARY)):
    raise ValueError(f"cat_idx out of range: {cat_idx}")
cat_items = PROMPT_LIBRARY[cat_idx].get("items") or []
if not (0 <= item_idx < len(cat_items)):
    raise ValueError(f"item_idx out of range: {item_idx}")
item = cat_items[item_idx]  # <-- возможен IndexError
```

**Проблема:** 
Хотя между проверкой `len(PROMPT_LIBRARY)` и доступом `PROMPT_LIBRARY[cat_idx]` нет `await` (атомарно), между доступом к `cat_items` и доступом к `item = cat_items[item_idx]` может произойти обновление `PROMPT_LIBRARY` в другом месте кода (в `_locked_save_and_refresh` → `refresh_prompt_library()`), что приведёт к `IndexError` на строке `item = cat_items[item_idx]`.

**Воспроизведение:**
1. Админ отправляет WebApp с `cat_idx=0, item_idx=3`
2. В момент строки `cat_items = PROMPT_LIBRARY[0].get("items")` в параллельном потоке обновляется PROMPT_LIBRARY (категория 0 теперь имеет 2 item-а вместо 4)
3. Проверка `0 <= 3 < 2` не была сделана → IndexError на строке `item = cat_items[item_idx]`

**Фикс:**
```python
cat_items = PROMPT_LIBRARY[cat_idx].get("items") or []
if not (0 <= item_idx < len(cat_items)):  # проверка ПОСЛЕ получения cat_items
    raise ValueError(f"item_idx out of range: {item_idx}")
item = cat_items[item_idx]
```

## 🟡 [SirNike.py:2896-2970] Несимметричная обработка исключений: `queued_user_ids.discard()` может пропуститься

**Код:**
```python
queued_user_ids.add(user.id)

state = get_or_init_state(context)

if not state.prompt:
    queued_user_ids.discard(user.id)
    await reply_target.reply_text(...)
    return
# ... ещё 5 точек выхода с discard ...
except BaseException as _enqueue_exc:
    queued_user_ids.discard(user.id)  # <-- последний discard
```

**Проблема:**
Множество ранних возвратов с вызовом `discard()`, но если какой-то из них забыт (a их 6 штук), то пользователь останется в `queued_user_ids` навсегда. Текущий код выглядит полным, но логика хрупкая.

**Воспроизведение:**
При рефакторинге легко забыть добавить `discard()` в новый `if`-блок.

**Фикс:**
Использовать `try-finally`:
```python
queued_user_ids.add(user.id)
try:
    if not state.prompt:
        await reply_target.reply_text("...")
        return
    # ... весь остальной код ...
finally:
    # Очистить только если не удалось enqueue успешно
    if user.id in queued_user_ids:
        queued_user_ids.discard(user.id)
```

## 🟡 [SirNike.py:2629-2640] Потеря URL при краше upload_image_bytes_to_imgbb

**Код:**
```python
async def upload_image_bytes_to_imgbb(image_bytes: bytes, filename: str = "import.jpg") -> Optional[str]:
    """Upload image bytes — tries freeimage.host → catbox.moe → imgbb."""
    url = await _upload_bytes_to_freeimage(image_bytes, filename)
    if url:
        return url
    url = await _upload_bytes_to_catbox(image_bytes, filename)
    if url:
        return url
    return await _upload_bytes_to_imgbb(image_bytes, filename)  # <-- может упасть
```

**Проблема:**
Если все три провайдера загрузки недоступны, последний вызов `_upload_bytes_to_imgbb()` выбросит исключение (не обработано в этой функции, хотя внутри оно логируется). Это исключение пройдёт выше и может потеряться в цепочке вызовов (например, в `build_seedance_reference_sheet_url`, строка 2709).

**Воспроизведение:**
Все API ключи не настроены или недоступны → `_upload_bytes_to_imgbb()` вернёт `None` → исключение при создании reference sheet.

**Фикс:**
```python
async def upload_image_bytes_to_imgbb(...) -> Optional[str]:
    for uploader in [_upload_bytes_to_freeimage, _upload_bytes_to_catbox, _upload_bytes_to_imgbb]:
        try:
            url = await uploader(image_bytes, filename)
            if url:
                return url
        except Exception as e:
            logger.warning("Upload attempt failed: %s", e)
    return None  # явный None вместо исключения
```

## 🟡 [SirNike.py:759-776] Утечка памяти в photo_tasks: таск может остаться в словаре при исключении

**Код:**
```python
async def send_done_later():
    try:
        await asyncio.sleep(2.0)
        count = photo_counts.pop(chat_id, 0)
        if count > 0:
            await context.bot.send_message(...)  # <-- может упасть
    except asyncio.CancelledError:
        pass
    finally:
        photo_tasks.pop(chat_id, None)
```

**Проблема:**
Если `send_message()` выбросит исключение **не** `CancelledError`, оно пройдёт дальше `except asyncio.CancelledError`, не будет обработано, и таск упадёт. При этом `finally` всё равно вызовется, но исключение всё ещё находится в воздухе и может быть залогировано как unhandled.

**Воспроизведение:**
Пользователь загружает фото → создаётся таск → через 2 сек попытка отправить сообщение падает с `BadRequest` → исключение не обработано → таск умирает, но `finally` выполнилась → потом попытка создать таск снова для того же chat_id → старый таск (упавший) остаётся в памяти в виде hanging exception.

**Фикс:**
```python
except asyncio.CancelledError:
    pass
except Exception:
    logger.exception("send_done_later failed for chat_id=%s", chat_id)
finally:
    photo_tasks.pop(chat_id, None)
```

## 🔴 [SirNike.py:1573–1590] Недостаточная валидация платёжного payload

**Код:**
```python
async def precheckout_callback(update: Update, context: ContextTypes.DEFAULT_TYPE):
    query = update.pre_checkout_query
    payload = query.invoice_payload
    try:
        parts = payload.split("_")
        if len(parts) < 3:
            raise ValueError("too few parts")
        count = int(parts[1])
        price = int(parts[2])
        if count <= 0:
            raise ValueError("non-positive count")
        valid_pack = next((p for p in BUY_PACKS if p["count"] == count and p["price"] == price), None)
        if valid_pack is None:
            raise ValueError(f"unknown pack count={count} price={price}")
    except Exception as e:
        logger.warning("Invalid precheckout payload %r from user %s: %s", payload, query.from_user.id, e)
        await query.answer(ok=False, error_message="Ошибка: неверный платёжный пакет.")
        return
    await query.answer(ok=True)
```

**Проблема:** Валидация не проверяет, что в payload ровно 3 части. Payload вида `buy_10_60_extra_data` пройдёт проверку `len(parts) < 3`, но лишние данные будут проигнорированы. Это позволяет злоумышленнику передать нестандартный payload, который может быть интерпретирован по-другому другими системами (prototype pollution через underscore-разделённые поля).

**Воспроизведение:** Отправить платёж с payload `buy_10_60_ADMIN_BYPASS` → части разделятся как `["buy", "10", "60", "ADMIN_BYPASS"]`, проверка `len(parts) < 3` пройдёт, и `parts[1]`, `parts[2]` будут взяты корректно, но лишние данные заполнят потенциальный injection-вектор.

**Фикс:** Явно проверить точное количество частей:
```python
if len(parts) != 3:
    raise ValueError(f"payload must have exactly 3 parts, got {len(parts)}")
```

## 🔴 [SirNike.py:1593–1628] Уязвимость TOCTOU при двойной обработке платежа

**Код:**
```python
async def successful_payment_callback(update: Update, context: ContextTypes.DEFAULT_TYPE):
    user = update.effective_user

    new_balance = get_balance(user.id)
```

**Проблема:** Между извлечением `count` из payload (строка 1610) и вызовом `save_payment_once()` (строка 1623) нет await, но сама функция `save_payment_once()` может быть асинхронной (не видно реализации в db.py). Если `save_payment_once()` — это async функция, то между проверкой `valid_pack` и вызовом функции будет лишь `await`, и race condition между двумя concurrent вызовами всё ещё возможен, если Telegram отправит обработчику duplicate webhook'и для одного платежа.

1. Пользователь делает платёж 10 изюминок за 60₽
2. Telegram отправляет duplicate webhook для того же платежа (технический сбой)
3. Оба обработчика одновременно вызывают `save_payment_once()` с одним и тем же payment_id

- Убедиться, что `save_payment_once()` действительно возвращает `False` при повторном вызове с тем же payment_id и проверить реализацию в db.py
- Добавить проверку, что `price` в payload соответствует текущему курсу в BUY_PACKS:
```python
expected_price = next((p["price"] for p in BUY_PACKS if p["count"] == count), None)
if expected_price != price:
    logger.error("Price mismatch: expected %d, got %d for count=%d", expected_price, price, count)

```

## 🟢 [SirNike.py:2896–2950] Потенциальный race condition при добавлении в очередь (низкий риск)

**Код:**
```python
async def run_generation(update: Update, context: ContextTypes.DEFAULT_TYPE):
    # ...
    queued_user_ids.add(user.id)

    state = get_or_init_state(context)

    if not state.prompt:
        queued_user_ids.discard(user.id)
        await reply_target.reply_text("Сначала отправь текст промпта.")
        return
```

**Проблема:** Хотя между `queued_user_ids.add()` и `if not state.prompt` нет await (атомарно в asyncio), **логика добавления в очередь не соответствует удалению из очереди**: если возникнет исключение между добавлением в `queued_user_ids` и вызовом `generation_queue.put_nowait()`, пользователь останется в `queued_user_ids` навечно и не сможет запустить генерацию снова (пока бот не перезагрузится).

**Воспроизведение:** Пользователь запускает генерацию → после добавления в `queued_user_ids` возникает исключение (например, `MemoryError` или неожиданный exception в `get_or_init_state()`) → `generation_queue.put_nowait()` не вызывается → пользователь остаётся в `queued_user_ids`, и при попытке повторной генерации получит ошибку "уже в очереди".

**Фикс:** Обернуть всю логику в try-finally:
```python
queued_user_ids.add(user.id)
try:
    # ... вся логика подготовки и добавления в очередь
finally:
    # Только если job успешно добавлена в очередь — не удаляем из queued_user_ids
    # В других случаях (исключения, отмены) — удаляем
    pass
```

Или переместить `queued_user_ids.add()` в конец перед `generation_queue.put_nowait()`.

Проанализировал код с фокусом на транзакции, схему и потерю данных. Учитывал архитектуру (однопоточный asyncio, один воркер).

## 🔴 [db.py:~136] `try_use_free_generation` — Lost update между двумя UPDATE

**Код:**
```python
def try_use_free_generation(user_id: int, max_per_day: int) -> bool:
    today = date.today().isoformat()
    with get_conn() as conn:
        # Case 1: date is today and count < max → increment
        cur = conn.execute(
            """UPDATE users
               SET free_used_count = free_used_count + 1
               WHERE user_id = ? AND free_used_date = ? AND free_used_count < ?""",
            (user_id, today, max_per_day),
        )
        conn.commit()
        if cur.rowcount > 0:
            return True
        # Case 2: date is not today (new day) → reset to 1
        cur = conn.execute(
            """UPDATE users
               SET free_used_date = ?, free_used_count = 1
               WHERE user_id = ? AND (free_used_date IS NULL OR free_used_date != ?)""",
            (today, user_id, today),
        )
        conn.commit()
        return cur.rowcount > 0
```

**Проблема:** Две отдельные `conn.commit()` между `UPDATE`ами. Если между Case 1 (возвращает False) и Case 2 другой процесс обновит `free_used_date = today`, то Case 2 тоже вернёт False, и функция вернёт False вместо True. Слот не будет потреблён, но баланс все равно будет потрачен — фото не будет сгенерировано бесплатно.

**Воспроизведение:**
1. Пользователь имеет `free_used_date = вчера`, `free_used_count = 0`
2. Запускает генерацию → `try_use_free_generation()` вызывает Case 2, успешно обновляет на `today`, возвращает True
3. **ИЛИ** (race) между Case 1 и Case 2 другой процесс/запрос обновляет `free_used_date` в ту же дату
4. Case 2 видит WHERE условие `free_used_date != today` = False, rowcount = 0
5. Функция возвращает False, хотя слот был доступен

**Фикс:** Объединить оба UPDATE в одну транзакцию с одной логикой:
```python
def try_use_free_generation(user_id: int, max_per_day: int) -> bool:
    today = date.today().isoformat()
    with get_conn() as conn:
        conn.execute("BEGIN")
        # Сначала SELECT FOR UPDATE эквивалент или проверка
        cur = conn.execute(
            "SELECT free_used_date, free_used_count FROM users WHERE user_id = ?",
            (user_id,)
        )
        row = cur.fetchone()
        if not row:
            conn.rollback()
            return False
        free_date, free_count = row
        
        if free_date == today:
            if free_count < max_per_day:
                conn.execute(
                    "UPDATE users SET free_used_count = free_used_count + 1 WHERE user_id = ?",
                    (user_id,)
                )
                conn.commit()
                return True
        else:
            conn.execute(
                "UPDATE users SET free_used_date = ?, free_used_count = 1 WHERE user_id = ?",
                (today, user_id)
            )
            conn.commit()
            return True
        
        conn.rollback()
        return False
```

## 🔴 [db.py:~313] `get_all_user_ids` — Возможна потеря ошибок в retry loop

**Код:**
```python
def get_all_user_ids(retries: int = 3) -> list:
    import time as _time
    for attempt in range(retries):
        try:
            with get_conn() as conn:
                cur = conn.cursor()
                cur.execute("SELECT user_id FROM users")
                return [row[0] for row in cur.fetchall()]
        except sqlite3.OperationalError as e:
            if attempt == retries - 1:
                logger.error("Failed to fetch user IDs after %d retries: %s", retries, e)
                raise
            _time.sleep(0.5 * (attempt + 1))
```

**Проблема:** Функция ловит только `sqlite3.OperationalError`. Но если случится `sqlite3.DatabaseError` или другой SQLite-вывод, он не будет перехвачен и сразу упадёт. В `SirNike.py` строка 1759+ (`broadcast_text`) и 1708+ (`broadcast_promo`) вызывают эту функцию без обработки исключений — рассылка упадёт полностью.

**Воспроизведение:**
1. БД повреждена или заблокирована нестандартно → `sqlite3.DatabaseError`
2. `get_all_user_ids()` не ловит это
3. `broadcast_text()` падает, `_broadcast_running` остаётся `True`
4. Следующая попытка рассылки мгновенно отклоняется из-за `if _broadcast_running:`

**Фикс:**
```python
def get_all_user_ids(retries: int = 3) -> list:

                cur = conn.cursor()

        except sqlite3.Error as e:  # Catch all SQLite errors
            if attempt == retries - 1:
                logger.error("Failed to fetch user IDs after %d retries: %s", retries, e)
                raise
            _time.sleep(0.5 * (attempt + 1))
```

## 🟡 [db.py:~155] `save_payment_once` — Потеря платежа при сбое после INSERT

**Код:**
```python
def save_payment_once(user_id: int, payment_id: str, amount: int) -> bool:
    with get_conn() as conn:
        try:
            conn.execute("BEGIN")
            cur = conn.execute(
                """
                INSERT INTO payments (user_id, telegram_payment_id, amount, created_at)
                VALUES (?, ?, ?, ?)
                """,
```
