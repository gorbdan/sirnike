### ❌ Отклонено верификатором


- **Race condition между `queued_user_ids.add()` и проверкой баланса** (SirNike.py:2896) — _по архитектурным фактам, asyncio ОДНОПОТОЧНЫЙ event loop; между `queued_user_ids.add()` и первым `await` (в `validate_image_url()`) нет race condition, это атомарно. Перехват исключений в `except BaseException` гарантирует очистку. Раннее падение перед `try` отловится в `except BaseException` на строке 3010._

- **Потенциальный deadlock в `_locked_save_and_refresh()`** (SirNike.py:517) — _`_get_prompt_library_lock()` вызывается только внутри async обработчиков (напр. callback для редактирования библиотеки), которые запускаются после инициализации event loop в `post_init()`. Timeout не требуется, т.к. `save_prompt_library()` блокирующий но быстрый (single json.dump). Нет starving — админский обработчик один на event loop._

## Security-аналитик платёжных систем

### ❌ Отклонено верификатором


- **Недостаточная валидация invoice_payload в precheckout_callback** (SirNike.py:1573) — _проверка `len(parts) < 3` уже гарантирует минимум 3 части; extra части просто игнорируются (безопасно). Отсутствие проверки `parts[0] == "buy"` — не уязвимость, так как payload генерируется только внутри `send_invoice()` со строгим форматом, клиент не может манипулировать. Telegram гарантирует целостность callback_data._

- **Отсутствует проверка `price > 0` в successful_payment_callback** (SirNike.py:1593) — _в `precheckout_callback` (строка 1573) нет явной проверки `price > 0`, но это безопасно: если `parts[2]` не распарсится в int ≤ 0, выбросится ValueError и payload будет отклонён. Кроме того, Telegram не отправит пречекаут с платежом стоимостью 0 (это блокируется API). Асимметрия в коде — не уязвимость._

- **Отсутствует валидация `count` и `price` в send_invoice перед отправкой счёта** (SirNike.py:1631) — _параметры `count` и `price` в `send_invoice()` идут из `button_handler` (строка ~3583), где парсятся из callback_data формата `buy_{count}_{price}`. Этот формат генерируется только кнопками в `buy()` (строка 1546) с валидными значениями из `BUY_PACKS`. Telegram гарантирует, что клиент не может отправить произвольный callback_data. Дополнительная проверка в `send_invoice()` — излишняя, так как проверка в `button_handler` уже гарантирует корректность._

- **Race condition между `create_user_if_not_exists` и `mark_referral_bonus`** (SirNike.py:1277) — _между `mark_referral_bonus()` и `add_izyminki()` нет race condition в asyncio-контексте, так как обе функции синхронные (без await между ними). Как указано в АРХИТЕКТУРНЫХ ФАКТАХ: любые две строки кода без await между ними выполняются атомарно в однопоточном event loop. Единственная точка уязвимости — на уровне SQL `mark_referral_bonus()`, но это в ответственности db-слоя, не SirNike.py._

- **Недостаточная валидация стоимости генерации перед добавлением в очередь** (SirNike.py:2896) — _`calc_generation_cost(references)` вызывается с `references` из `state.references`, который заполняется через `handle_photo()` (строка ~2168) с лимитом в код (не видно явного лимита, но list операции ограничены памятью). Более того, функция проверяет баланс и списывает средства атомарно после расчёта стоимости, так что переполнение не приведёт к некорректному платежу — неправильная стоимость будет просто отклонена при проверке баланса. Отрицательная стоимость физически невозможна (количество фото всегда ≥ 0)._

- **Отсутствует лимит на размер в cache_media_group_message при достижении TTL** (SirNike.py:1160) — _это не уязвимость, а известное архитектурное свойство. Временное превышение `MAX_CACHED_MEDIA_GROUPS` перед срабатыванием eviction — нормально; кеш OrderedDict вмещает память спокойно (300 групп × ~10KB = 3MB макс). Код явно учитывает это ("Hard cap")._

- **Использование username для идентификации в логах платежей** (SirNike.py:1277) — _использование `user.username` в логах и базе — нормально для Telegram-ботов; `user.id` — primary key, username — справочная информация. Проверка на None — хорошая практика, но отсутствие её не является bug'ом; `create_user_if_not_exists()` из db.py сам должен обрабатывать None gracefully. Это не уязвимость в SirNike.py._

## 🔴 [SirNike.py:1277-1310] Гонка в реферальной системе при одновременной регистрации двух новых пользователей с одной ссылкой

**Код:**
```python
is_new_user = create_user_if_not_exists(user.id, user.username, START_BONUS, referrer_id=referrer_id)

if referrer_id and is_new_user and mark_referral_bonus(user.id):
    try:
        add_izyminki(user.id, REFERRAL_BONUS_NEW_USER)
        add_izyminki(referrer_id, REFERRAL_BONUS_REFERRER)
```

**Проблема:** 
`mark_referral_bonus(user.id)` вызывается **после** `create_user_if_not_exists`, но функция возвращает просто bool. Если двое пользователей A и B пришли одновременно по реферальной ссылке user_id=123 (реферер), то оба заходят в условие `if referrer_id and is_new_user`, оба прошли `create_user_if_not_exists`, и оба вызывают `mark_referral_bonus(user.id)` для своего user_id. Однако если `mark_referral_bonus` проверяет флаг "бонус за реферала уже начислен", а не "это новый пользователь", то система корректна. Но если `mark_referral_bonus` — это просто `UPDATE` без уникального ограничения, то **оба пользователя получат REFERRAL_BONUS_NEW_USER**, и реферер получит 2× REFERRAL_BONUS_REFERRER вместо 1× за каждого.

**Воспроизведение:** 
1. Шарю две ссылки `/ref_123` в чат (или один друг использует её дважды в разных чатах параллельно)
2. Оба новых пользователя регистрируются в пиковый момент (< 1 сек между ними)
3. Оба проходят мимо `mark_referral_bonus` и получают бонусы

**Фикс:** 
Убедиться, что `mark_referral_bonus` использует уникальный индекс `(user_id)` в БД с `INSERT IGNORE` или `INSERT ... ON CONFLICT DO NOTHING`, чтобы только первый вызов записал флаг. Или добавить проверку `has_referral_bonus(user.id)` **перед** начислением:
```python
if referrer_id and is_new_user and not has_referral_bonus(user.id):
    if mark_referral_bonus(user.id):
        add_izyminki(user.id, REFERRAL_BONUS_NEW_USER)
        add_izyminki(referrer_id, REFERRAL_BONUS_REFERRER)
```
