async def balance(update: Update, context: ContextTypes.DEFAULT_TYPE):

## 🔴 [SirNike.py:1582–1601] Отсутствие повторного воспроизведения платежа (Replay Attack Prevention)

**Код:**
```python
async def precheckout_callback(update: Update, context: ContextTypes.DEFAULT_TYPE):
    query = update.pre_checkout_query
    payload = query.invoice_payload
    try:
        parts = payload.split("_")
        if len(parts) < 3:
            raise ValueError("too few parts")
        count = int(parts[1])
        price = int(parts[2])
        if count <= 0:
            raise ValueError("non-positive count")
        valid_pack = next((p for p in BUY_PACKS if p["count"] == count and p["price"] == price), None)
        if valid_pack is None:
            raise ValueError(f"unknown pack count={count} price={price}")
    except Exception as e:
        logger.warning("Invalid precheckout payload %r from user %s: %s", payload, query.from_user.id, e)
        await query.answer(ok=False, error_message="Ошибка: неверный платёжный пакет.")
        return
    await query.answer(ok=True)
```

**Проблема:** В `precheckout_callback` отсутствует проверка дублирования платежей. Telegram гарантирует доставку pre_checkout_query, но если боту удалось ответить `ok=True`, а потом произойдёт сетевой сбой и переподача того же запроса — платёж может быть авторизован дважды. Нет сохранения `pre_checkout_query_id` в БД перед ответом.

**Воспроизведение:** 
1. Юзер нажимает «Купить 50 изюминок»
2. Telegram отправляет `pre_checkout_query` с `query_id=ABC123`
3. Бот валидирует и отвечает `ok=True`
4. Сетевой сбой — Telegram не получил ответ и переотправляет `pre_checkout_query`
5. Боту приходит снова тот же `query_id=ABC123`, бот снова отвечает `ok=True`
6. Оба ответа доходят до Telegram → может привести к двум попыткам платежа

**Фикс:** 
```python
async def precheckout_callback(update: Update, context: ContextTypes.DEFAULT_TYPE):
    query = update.pre_checkout_query
    pre_checkout_id = query.id  # Уникальный ID от Telegram
    
    # Проверить, не обработан ли уже этот pre_checkout_query
    if is_precheckout_processed(pre_checkout_id):
        await query.answer(ok=True)  # идемпотентно ответить снова
        return
    
    # ... валидация payload ...
    
    # Сохранить факт обработки ДО ответа Telegram
    mark_precheckout_processed(pre_checkout_id)
    await query.answer(ok=True)
```

## 🔴 [SirNike.py:1602–1640] TOCTOU при обработке платежа: gap между check и credit

**Код:**
```python

        valid_pack = next((p for p in BUY_PACKS if p["count"] == count and p["price"] == price), None)
        if valid_pack is None:

    except Exception as e:
        logger.error("Invalid payment payload %r from user %s: %s", payload, user.id, e)
        await update.message.reply_text("Ошибка обработки платежа. Обратись в поддержку.")
        return

    if not save_payment_once(user.id, payment_id, count):
        await update.message.reply_text("Платёж уже обработан.")
        return

    # add_izyminki is now done atomically inside save_payment_once
    new_balance = get_balance(user.id)
```

**Проблема:** Код комментирует, что `add_izyminki` выполняется атомарно внутри `save_payment_once`. Однако в файле `SirNike.py` нет видимого определения `save_payment_once`. Если эта функция из `db.py` НЕ гарантирует атомарность на уровне БД (т.е. не использует транзакции), то между проверкой "платёж уже обработан" и кредитом может произойти:

1. `save_payment_once` возвращает `True` (платёж не был ещё в БД)
2. Но перед `add_izyminki` боту отправляется исключение / происходит краш
3. Платёж записан в БД, но изюминки не добавлены
4. При перезапуске бота платёж уже в БД → не будет переобработан

**Воспроизведение:**
1. Юзер платит, Telegram отправляет `successful_payment`
2. `save_payment_once` проверяет БД, не видит платёж (он первый раз) → `True`
3. Функция начинает писать платёж в БД
4. Но на строке между записью в БД и вызовом `add_izyminki` происходит crash (OutOfMemory, сегментация и т.д.)
5. Новая попытка сообщения `successful_payment` (Telegram пересылает) → уже в БД, возвращает `False`
6. Юзер никогда не получит изюминки

**Фикс:** Убедиться, что `save_payment_once` в `db.py` использует транзакцию:
```python
def save_payment_once(user_id: int, payment_id: str, count: int) -> bool:
    conn = sqlite3.connect(DB_NAME)
    conn.execute("BEGIN IMMEDIATE")  # Exclusive lock
    try:
        cursor = conn.cursor()
        cursor.execute("SELECT id FROM payments WHERE telegram_charge_id = ?", (payment_id,))
        if cursor.fetchone():
            conn.rollback()
            return False
        cursor.execute(
            "INSERT INTO payments (user_id, telegram_charge_id, amount) VALUES (?, ?, ?)",
            (user_id, payment_id, count)
        )
        cursor.execute(
            "UPDATE users SET balance = balance + ? WHERE id = ?",
            (count, user_id)
        )
        conn.commit()
        return True
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()
```

## 🟡 [SirNike.py:2912-3030] Race condition в `run_generation` между проверкой баланса и его списанием

**Фикс:** Добавить проверку `if user.id in processing_user_ids: return` сразу после `queued_user_ids.add()` и до финального `generation_queue.put_nowait()`.

### ❌ Отклонено верификатором


- **Потеря данных при одновременной выплате бонуса за реферала** (db.py:103) — _asyncio однопоточный. Оба процесса не могут одновременно находиться в `create_user_if_not_exists`. SQLite INSERT OR IGNORE с UNIQUE constraint гарантирует, что только один INSERT сработает. Проверка `is_new` по `cur.rowcount` корректна. В SirNike.py (1293-1301) после create_user_if_not_exists идёт if без await, значит проверка и mark_referral_bonus выполняются атомарно в одном потоке._

- **Недостающая транзакция при обновлении свободных генераций** (db.py:189) — _`try_use_free_generation` существует и используется в SirNike.py (2945). Функция `use_free_generation` — это отдельная утилита без проверки лимита, но в коде она вызывается только в специфических местах, где лимит уже проверен или не критичен. Тот факт, что существует `try_use_free_generation` (с правильной атомарной логикой), не значит, что `use_free_generation` — баг._

- **Потеря данных при отказе шага 1 в save_payment_once** (db.py:321) — _логика корректна. INSERT с UNIQUE constraint либо вставит одну строку (rowcount=1), либо выбросит IntegrityError (если дубликат). Проверка `if cur.rowcount == 0` — мёртвый код, но не баг. Транзакция откатывается при IntegrityError, что правильно._

- **Недостающий лимит в get_generation_history при DoS-атаке** (db.py:378) — _это не баг в коде. Функция используется в SirNike.py через обработчик команд, и там должна быть валидация на уровне вызывающей стороны. Функция db просто выполняет что ей скажут. Без ссылки на конкретный вызов с невалидированным параметром — не подтверждено._

- **Потенциальная потеря данных при вызове add_izyminki с отрицательным значением** (db.py:82) — _`add_izyminki` используется только для выдачи бонусов и админ-команд, где контроль на уровне приложения (SirNike.py:1969 проверяет `amount > 0` перед вызовом). Отсутствие проверки в самой функции — это проектное решение (функция —helper для доверенных вызовов), а не баг. Баг был бы, если бы это вызывалось с неконтролируемым пользовательским вводом напрямую, но это не так._
