## 🔴 [SirNike.py:1623-1640] Отсутствует валидация payload в precheckout_callback

**Код:**
```python
async def precheckout_callback(update: Update, context: ContextTypes.DEFAULT_TYPE):
    query = update.pre_checkout_query
    payload = query.invoice_payload
    try:
        parts = payload.split("_")
        if len(parts) < 3:
            raise ValueError("too few parts")
        count = int(parts[1])
        price = int(parts[2])
        if count <= 0:
            raise ValueError("non-positive count")
        valid_pack = next((p for p in BUY_PACKS if p["count"] == count and p["price"] == price), None)
        if valid_pack is None:
            raise ValueError(f"unknown pack count={count} price={price}")
    except Exception as e:
        logger.warning("Invalid precheckout payload %r from user %s: %s", payload, query.from_user.id, e)
        await query.answer(ok=False, error_message="Ошибка: неверный платёжный пакет.")
        return
    await query.answer(ok=True)
```

**Проблема:** Функция проверяет корректность payload, но **не защищена от TOCTOU-атаки** (Time-of-Check-Time-of-Use). Проверка в `precheckout_callback` и фактическое списание в `successful_payment_callback` — это две отдельные точки, между которыми может произойти:
1. Изменение конфига `BUY_PACKS` (добавление/удаление пакетов)
2. Манипуляция состоянием базы данных

Вторая проверка в `successful_payment_callback` (строки 1643-1678) дублирует валидацию, но это не гарантирует атомарность.

**Воспроизведение:**
1. Пользователь нажимает купить пакет (payload валидируется в `precheckout_callback`)
2. Админ изменяет `BUY_PACKS` (удаляет этот пакет) между пречекаутом и завершением платежа
3. `successful_payment_callback` отклоняет платёж как "неизвестный пакет", но Telegram уже списал деньги
4. Средства у пользователя не зачисляются → деньги потеряны

**Фикс:** Сохранить валидированную информацию о пакете (count, price) в памяти воркера или базе при пречекауте, использовать эту сохранённую копию в `successful_payment_callback`, а не перепроверять против текущего конфига BUY_PACKS.

## 🔴 [SirNike.py:1643-1680] Race condition при обработке платежа между spend и сохранением

**Код:**
```python
async def successful_payment_callback(update: Update, context: ContextTypes.DEFAULT_TYPE):
    user = update.effective_user
    payment = update.message.successful_payment
    payment_id = payment.telegram_payment_charge_id
    payload = payment.invoice_payload

    try:
        parts = payload.split("_")
        if len(parts) < 3:
            raise ValueError("too few parts")
        count = int(parts[1])
        price = int(parts[2])
        if count <= 0 or price <= 0:
            raise ValueError("non-positive count or price")
        valid_pack = next((p for p in BUY_PACKS if p["count"] == count and p["price"] == price), None)
        if valid_pack is None:
            raise ValueError(f"unknown pack count={count} price={price}")
    except Exception as e:
        logger.error("Invalid payment payload %r from user %s: %s", payload, user.id, e)
        await update.message.reply_text("Ошибка обработки платежа. Обратись в поддержку.")
        return

    if payment.total_amount != valid_pack["price"] * 100:
        logger.error("Payment amount mismatch: expected %d kopecks, got %d, user=%s",
                     valid_pack["price"] * 100, payment.total_amount, user.id)
        await update.message.reply_text("Ошибка: сумма платежа не совпадает. Обратись в поддержку.")
        return

    if not save_payment_once(user.id, payment_id, count):
        await update.message.reply_text("Платёж уже обработан.")
        return

    # add_izyminki is now done atomically inside save_payment_once
    new_balance = get_balance(user.id)
```

**Проблема:** Комментарий говорит "atomically inside save_payment_once", но при обращении к `get_balance()` после `save_payment_once()` **нет await между ними — это семантически одна операция в asyncio**, однако код полагается на атомарность `save_payment_once` без видимого механизма предотвращения двойного зачисления. Если `save_payment_once` вернёт `True` дважды (из-за race в `db.py`), будут зачислены удвоенные изюминки.

**Воспроизведение:** Telegram отправляет `successful_payment` с идентичным `payment_id` дважды за короткий промежуток (сетевая переотправка). Если в `db.py` функция `save_payment_once` не использует database-level UNIQUE constraint на `(user_id, payment_id)`, а полагается на SELECT + INSERT, — изюминки могут быть зачислены дважды.

**Фикс:** Убедиться, что в `db.py` функция `save_payment_once` использует SQL `INSERT OR IGNORE` / `ON CONFLICT DO NOTHING` с UNIQUE constraint на столбцы `user_id` и `payment_id`. Без этого — добавить логирование попыток двойной обработки платежа в `db.py`.

## 🔴 [db.py:195] Неатомарная проверка баланса и списание в spend_izyminki

**Код:**
```python
def spend_izyminki(user_id: int, amount: int) -> bool:
    with get_conn() as conn:
        cur = conn.cursor()
        cur.execute(
            """
            UPDATE users
            SET balance = balance - ?
            WHERE user_id = ? AND balance >= ?
            """,
            (amount, user_id, amount)
        )
        conn.commit()
        return cur.rowcount > 0
```

**Проблема:** Хотя UPDATE с WHERE условием выглядит атомарно, в `sqlite3` по умолчанию используется `AUTOCOMMIT=False`. Это значит, что между `execute()` и `commit()` открыта транзакция. Если процесс упадёт между ними, коммит не произойдёт, но `rowcount` уже будет > 0. В следующей попытке пользователь может повторить запрос и получить false при неудаче, оставляя баланс в неопределённом состоянии. Критично при падении сервера сразу после `execute()`.

**Воспроизведение:** 
1. Пользователь нажимает "Генерировать" (cost=10)
2. `spend_izyminki()` выполняет UPDATE (баланс 20→10) и `rowcount=1`
3. До `commit()` процесс падает
4. БД откатывается, баланс остаётся 20
5. После перезапуска пользователь может повторить и снова потратить те же 10 изюминок

**Фикс:** Явно начинать транзакцию перед UPDATE:
```python
def spend_izyminki(user_id: int, amount: int) -> bool:
    with get_conn() as conn:
        try:
            conn.execute("BEGIN")
            cur = conn.execute(
                "UPDATE users SET balance = balance - ? WHERE user_id = ? AND balance >= ?",
                (amount, user_id, amount)
            )
            result = cur.rowcount > 0
            conn.commit()
            return result
        except Exception:
            conn.rollback()
            raise
```

## 🔴 [db.py:165] Race condition в add_izyminki при одновременных обновлениях

**Код:**
```python
def add_izyminki(user_id: int, amount: int):
    with get_conn() as conn:
        cur = conn.execute(
            "UPDATE users SET balance = balance + ? WHERE user_id = ?",
            (amount, user_id)
        )
        conn.commit()
        return cur.rowcount > 0
```

**Проблема:** SQLite использует уровень изоляции `SERIALIZABLE` по умолчанию, но только если не открывается несколько соединений одновременно. Каждый вызов `get_conn()` открывает **новое соединение**. Два одновременных `add_izyminki()` из разных asyncio тасков могут получить старое значение balance в памяти и перезаписать друг друга. Пример: баланс=100, два тaska добавляют по 50 → может остаться 150 вместо 200.

Архитектурный факт: asyncio однопоточный, но `get_conn()` всегда создаёт новое соединение SQLite, что нарушает изоляцию.

**Воспроизведение:**
1. `await asyncio.gather(add_izyminki(user, 50), add_izyminki(user, 50))`
2. Оба таска открывают разные подключения к БД
3. Оба читают balance=100, оба пишут 100+50=150
4. Результат: 150 вместо 200

**Фикс:** Использовать одно глобальное соединение с сохранением ACID или использовать PRAGMA synchronous:
```python
_DB_CONN = None
def get_conn():
    global _DB_CONN
    if _DB_CONN is None:
        _DB_CONN = sqlite3.connect(DB_NAME, check_same_thread=False)
        _DB_CONN.isolation_level = None  # AUTOCOMMIT mode
    return _DB_CONN
```

## 🟡 [SirNike.py:2732-2790] Потенциальная утечка памяти в build_seedance_reference_sheet_url
