# Живой аудит вебаппа на проде (https://sirnike.pages.dev)

Дата: 2026-08-17
Метод: ручной прогон через Browser (desktop 1280×720 + mobile 375×812,
светлая и тёмная тема), сверка через DOM/JS-инспекцию (не только визуально).
Экраны: «Создать», «Стили» (библиотека), «Доски», «Студия мультиков».

================================================================
🔴 КРИТИЧНОЕ
================================================================

### 1. Каталог «Стили»: страница «прыгает» по скроллу сама по себе,
    клик по карточке открывает ДРУГОЙ стиль

Шаги: «Стили» → проскроллить к любой строке категории → подождать
1–3 сек, ничего не нажимая. Скролл-позиция страницы самопроизвольно
скачет (наблюдала прыжок на ~600px вверх без единого действия
пользователя, шапка и первая категория то исчезают за пределы экрана,
то возвращаются). Пока это происходит, клик по видимой карточке может
открыть модалку СОВСЕМ ДРУГОГО стиля — воспроизведено: клик по карточке
«С цветами» (сиреневый букет) открыл модалку «Пляж и море» («Синий час у
моря… бокал шампанского»), с чужим prompt и чужим «Что загрузить».

Технически: у самих `<img>` в карточках `loading="lazy"`, атрибутов
width/height нет, но родительский контейнер карточки резервирует высоту
(290px, фиксирован) — точечно CLS не должен возникать на уровне одной
карточки. Прыжки, скорее всего, идут от категорий/строк целиком —
похоже на пересчёт высоты контейнера при догрузке данных категории
(виртуализация/lazy-fetch строк?) уже ПОСЛЕ первого рендера, из-за чего
браузер не может держать якорь скролла. Точную причину пусть локализует
фронтенд по DOM/сети — воспроизводится стабильно, не единичный глюк.

Почему критично: это ровно то же семейство бага, что уже ловили на
стороне бота (audits/2026-07-31_live_bot_ux_test.txt, находки №1–2 —
«Использовать» на «Новинках» падает/путает title из-за рассинхрона
позиции элемента). Здесь та же болезнь видна ещё РАНЬШЕ, на стороне
вебаппа, до всякой отправки данных боту: пользователь визуально видит
одну карточку, а получает промт другой. Для монетизации это хуже
всего — человек может запустить генерацию с промтом, который не
выбирал, потратить изюминки и не понять, почему результат не похож на
то, что он видел.

ФИКС: приоритет — найти источник пересчёта layout (React key/index
завязан на позицию в массиве, а не на стабильный id стиля? категории
domусираются/перевставляются при скролле?) и убрать скачки скролла;
дополнительно — резолвить клик по стабильному id карточки, а не по
текущей DOM-позиции, чтобы даже при реальном layout shift открывался
верный стиль.

### 2. Закрытие модалки стиля не всегда реагирует с первого раза

При тесте находки №1 модалка не закрылась ни по клику на «✕», ни по
Escape с первой попытки — закрылась только по клику на затемнённый фон.
Не до конца ясно, совпадение ли это с находкой №1 (тот же layout-shift
мог сдвинуть кнопку «✕» под курсором) — но если баг независимый, у
пользователя есть шанс «залипнуть» в модалке. Перепроверить после
фикса №1 — если сохранится, разбирать отдельно.

### 3. Скролл каталога сбрасывается в начало при закрытии модалки

Открыла карточку из середины длинного списка (после скролла на ~900px)
→ закрыла модалку → страница вернулась в самый верх каталога, а не на
то место, где была карточка. Мелкое раздражение при просмотре большого
каталога — приходится каждый раз скроллить заново.

### 4. Пустые экраны «Доски» и «Студия» — просто рамка+текст на всю
    высоту экрана

Оба экрана при пустом состоянии — один маленький элемент (пунктирный
квадрат «+» или кнопка «Новый мультик») в углу, дальше — пустое
пространство до низа экрана. Не баг, но ощущается недоделанным на фоне
аккуратно свёрстанного экрана «Создать». Не приоритет, но раз просили
«идеальный интерфейс» — стоит сделать пустые состояния визуально
законченными (иллюстрация/центрирование/пояснение «как это работает»),
как уже сделано на «Создать».

### 5. Мобильная версия (375px) — «Создать» ок, «Стили» не проверила
    полноценно из-за находки №1

На 375px экран «Создать» — чистая раскладка 2×2 + широкая карточка,
тап-зоны достаточного размера. Каталог «Стили» на мобильном скорее всего
подвержен той же находке №1 (общий код) — перепроверить отдельно
ПОСЛЕ фикса №1, сейчас смысла нет.

================================================================
ЧТО РАБОТАЕТ ХОРОШО
================================================================

- Тёмная тема — чистая, контрастная, переключается мгновенно
  (`data-theme` на `<html>`), не ломает раскладку.
- Кнопки «В избранное» на карточках — у всех есть `aria-label`
  («В избранное»), доступны для скринридера.
- Раскладка «Создать» (2×2 + широкая карточка) — аккуратная и на
  desktop, и на mobile.
- Фильтры каталога («Все» / «Новинки» / «Фото» / «Видео» / «Избранное»)
  и выпадающий список категорий — работают, не нашла нареканий.

### 6. 🔴 Первая же загрузка страницы качает ~13 видео целиком + по кругу —
    приложение зависает на десятки секунд

На заходе на «Создать» (там нет ни одного видео на экране — только 5
статичных плиток Фото/Видео/Аватар/Midjourney/Улучшить фото) сеть сразу
уходит в загрузку 13 файлов `/videos/*.mp4` ПОЛНОСТЬЮ (`200`, не
`206 Partial Content` — то есть не ленивый рейндж для метаданных, а
весь файл). Через доли секунды те же 13 файлов запрашиваются ПОВТОРНО —
уже рейндж-запросами, и большинство сразу обрываются
(`net::ERR_ABORTED`) и перезапускаются снова: за первые ~150мс после
загрузки в логе сети — свыше 30 запросов к одному и тому же набору из
13 роликов. Похоже на два независимых конкурирующих загрузчика превью
(вероятно, `<video preload="auto">` в скрытых DOM-карточках категории
«Стили» + отдельный JS-прелоадер), из-за чего происходит гонка
play/abort/reload по кругу.

Эффект на живом прогоне: клики через `computer.left_click` (синтетические
события ввода) переставали доходить до страницы — таймаут 30 сек,
приложение выглядело полностью зависшим. DOM при этом был жив и
кликабелен программным `.click()` через JS (значит, не краш рендерера,
а перегрузка event loop/сети настолько сильная, что реальный тап
пользователя не успевает быть обработан вовремя). На мобильной сети/
слабом устройстве внутри Telegram WebView это будет ощутимо хуже, чем
в десктоп-браузере, где тестировала — не исключаю, что это и есть
причина жалоб на «тормозит»/«зависает», если такие есть.

ФИКС: превью в карточках категорий (видео-стили типа Seedance 2) не
должны эагерли/полностью грузить исходный `.mp4` при первом рендере
экрана «Создать» — только постер-картинка + подгрузка видео по
реальному входу во вьюпорт (IntersectionObserver) или по явному тапу.
Также найти и убрать дублирующийся загрузчик — 2 независимых источника
запросов на один и тот же файл это отдельный баг сам по себе, даже если
ленивую загрузку не делать.

### 7. 🟡 «Студия мультиков»: заголовок обрезает переключатель темы

На экране «Студия мультиков» длинный заголовок вкладки выталкивает
последнюю иконку хедера (переключатель тёмной темы 🌙) за правый край
вьюпорта на 375px — виден только вертикальный обрезок ~5px. На «Создать»/
«Стили»/«Доски» все 3 иконки хедера влезают полностью. Нужен flex-shrink
на заголовке или уменьшение кегля на узких экранах.

### 8. 🟢 Активная вкладка нижнего меню не синхронизируется при переходе
    через плитку

Открыла «Midjourney» с экрана «Создать» (это отдельный экран, не таб
нижнего меню) после того, как до этого была на вкладке «Студия» —
нижняя навигация продолжает подсвечивать «Студия» красным, хотя
фактически открыт совсем другой экран. Мелочь, но сбивает ориентацию.

Итог дополнения: находка №6 — по факту такой же блокер, как №1 (тоже
«приложение неюзабельно», просто с другим триггером — перегрузка сети/
event loop вместо неверного клика), только шире по эффекту: ловит
КАЖДОГО пользователя на первом же открытии, а не только тех, кто
кликает по каталогу во время скролл-прыжка. Проверять и чинить в связке
с находкой №1 — оба про «интерфейс не готов к реальному использованию»,
а не про полировку.
