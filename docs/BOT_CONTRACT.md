# Контракт бот ↔ вебапп «Библиотека стилей»

Вебапп живёт в отдельном репо (Cloudflare Pages, https://sirnike.pages.dev).
Бот синкает `prompt_library.json` из вебаппа при старте — **source of truth = репо вебаппа**.
Парсер на стороне бота: `apply_webapp_prompt_payload_v2` (SirNike.py, ~строка 3096).

## prompt_library.json

Массив категорий:

```json
[
  {
    "title": "Название категории",
    "emoji": "🎬",
    "items": [
      {
        "title": "Название стиля",        // у ФОТО-стилей отсутствует НАМЕРЕННО — не дописывать!
        "prompt": "полный промт",
        "type": "video",                   // отсутствует = фото
        "video_url": "...", "poster_url": "...",   // для видео
        "example_url": "...",              // для фото
        "image_prompt": "...",             // опц.: промт стилизации кадра перед видео
        "description": "описание для карточки",
        "upload_hint": "Фото лица + 5 фото одежды", // что загрузить юзеру
        "input_hint": "Опиши свои пожелания (необязательно)", // опц.: показывает в модалке текстовое поле,
                                                                // введённый текст уходит в payload как note/n
        "style_extract": true,                             // опц.: см. раздел «Двух-референсные стили» ниже
        "added_at": "ISO-дата"
      }
    ]
  }
]
```

⚠️ У фото-стилей `title` отсутствует намеренно (решение владельца, карточки фото
без подписей — НЕ дописывать). Бот берёт fallback-лейбл (`_showcase_item_label`)
по `cat_idx`/`item_idx`, которые вебапп шлёт в каждом payload. У видео `title` заполняется.

**Исключение (2026-07-15, решение владельца):** у категории **💄 Бьюти** `title`
заполнен у всех фото-стилей — по её отдельной просьбе, специально для этой
категории. Остальные категории — правило «без title» остаётся в силе.

## Payload web_app_data (вебапп → бот)

JSON строкой. Полные и короткие ключи равнозначны:

| Поле | Кратко | Значение |
|---|---|---|
| `action` | `a` | `set_prompt` \| `set_video_prompt` \| `set_prompt_ref` \| `set_video_prompt_ref` \| `topup` \| `board_refs` (+ алиасы `apply_prompt`, `use_prompt`, `apply_template`, `connect_board`, `br`…) |
| `title` | `t` | название стиля (показывается юзеру); для `board_refs` — название доски |
| `prompt` | `p` | полный промт |
| `image_prompt` | — | опц., промт стилизации кадра для видео |
| `cat_idx` | `ci` | fallback: индексы вместо промта, |
| `item_idx` | `ii` | если payload не влезает — бот резолвит промт локально |
| `note` | `n` | опц., свободный текст юзера из поля `input_hint` — бот дописывает его в конец промта после резолва (см. `apply_webapp_prompt_payload_v2`), пусто = промт уходит как есть |
| `board_refs` | `br` | доски (MVP), см. ниже — массив уже захостенных на imgbb URL фото доски |

Правила:
- Payload > лимита Telegram → слать только `ci`/`ii` + `a` (+ `note`, если заполнен), без `p`.
- `topup` открывает у бота экран пополнения.
- Менять формат payload или структуру JSON — только синхронно с правкой парсера в боте
  (бриф бэкенду в `docs/briefs/backend.md` в репо бота).

## Доски (mood-борды), MVP (2026-08-09)

По [docs/specs/2026-08-09_mood_boards.md](specs/2026-08-09_mood_boards.md). Доски
целиком хранятся на стороне вебаппа (localStorage) — **бот их не хранит**, только
принимает уже захостенные фото активной доски и кладёт их в свой буфер референсов
для следующей генерации. Никакого AI-анализа стиля на MVP-этапе (это Full,
отдельная будущая задача).

Payload при «✅ Сделать активной и продолжить» (Экран 2 спеки), тем же
механизмом (`tg.sendData` / `answerWebAppQuery`), что и обычное «Использовать»:

```json
{"action": "board_refs", "title": "Вечерний гламур", "board_refs": ["https://i.ibb.co/...", "..."]}
```

- `board_refs`/`br` — массив URL (уже захостенных на imgbb той же Cloudflare
  Function, что используется для Студии нейромультиков) — до 10 в самой доске,
  бот берёт **первые 8** (существующий потолок референсов на одну генерацию,
  `_append_reference_url` в SirNike.py — общий код с ручной загрузкой фото), остальные
  молча не идут в референс (не баг).
- `title`/`t` — название доски (в этом экшене НЕ название стиля).
- Бот отвечает в чат подтверждением (текст зафиксирован спекой дословно) +
  кнопкой «📚 Библиотека стилей» — дальше юзер идёт по обычному пути выбора
  стиля, применение стиля НЕ трогает фото доски (они уже в буфере референсов).
- `note`/`n` в этом действии не используется и не читается ботом — не путать
  с «свои пожелания» юзера к конкретному стилю (другая сущность,
  [docs/specs/2026-07-17_note_override_weak.md](specs/2026-07-17_note_override_weak.md)).
- Реализация на стороне бота: `apply_webapp_board_refs_payload` (SirNike.py).

## Инлайн-путь «Использовать» в 1 тап (Cloudflare Function, вариант B)

Решение по [docs/specs/2026-07-15_webapp_inline_1tap.md](specs/2026-07-15_webapp_inline_1tap.md)
принято 2026-07-16: **вариант B**. `sendData()` работает только для вебаппа,
открытого с reply-клавиатуры (`persistent_menu_kb`) — это НЕ меняется,
остаётся основным путём. Для вебаппа, открытого с ИНЛАЙН-кнопки (`main_menu_kb`,
`result_actions_kb` — там, где сейчас 2-таповый обход через `pl_open_webapp`),
добавляется отдельный путь через `answerWebAppQuery`:

1. Вебапп открыт с инлайн-кнопки → `tg.initDataUnsafe.query_id` присутствует.
2. Тап «Использовать» → вместо `tg.sendData()` вебапп шлёт `POST` на Cloudflare
   Function (репо вебаппа, `/functions/answer-webapp-query` или аналогично —
   путь фронтенд выбирает сам) с телом:
   ```json
   {"init_data": "<tg.initData как есть>", "cat_idx": 3, "item_idx": 7, "note": ""}
   ```
3. Function проверяет HMAC-подпись `init_data` секретом `BOT_TOKEN` (алгоритм
   — офиц. доки Telegram, "Validating data received via the Mini App"), достаёт
   `query_id`, отклоняет запрос при невалидной подписи.
4. Function вызывает Telegram Bot API напрямую (`fetch`, без SDK):
   ```
   POST https://api.telegram.org/bot<BOT_TOKEN>/answerWebAppQuery
   {
     "web_app_query_id": "<query_id из initData>",
     "result": {
       "type": "article",
       "id": "pl_use_3_7",
       "title": "Использовать стиль",
       "input_message_content": {"message_text": "📚 Стиль подобран — жми ниже 👇"},
       "reply_markup": {"inline_keyboard": [[
         {"text": "🚀 Использовать", "callback_data": "pl_use_3_7"}
       ]]}
     }
   }
   ```
5. Telegram сам вставляет это сообщение в чат юзера с ботом. Тап по кнопке —
   обычный `callback_query` с `callback_data=pl_use_{cat_idx}_{item_idx}`,
   бот обрабатывает его существующим хэндлером `button_handler` → ветка
   `pl_use_` (SirNike.py) — тот же код, что у инлайн-каталога библиотеки
   внутри бота. Дублировать логику применения стиля не пришлось.
6. Вебапп после успешного ответа Function вызывает `tg.close()`. При сетевой
   ошибке — показать тост, `tg.close()` не звать (см. критерий приёмки в спеке).

⚠️ **У кнопки под answerWebAppQuery-сообщением `query.message` в боте
ВСЕГДА `None`** (Bot API: у `CallbackQuery` ровно одно из полей
`message`/`inline_message_id`, для инлайн-сообщений — второе). Раньше
`pl_use_` отвечал через `query.message.reply_text(...)` и падал молча
(живой баг 2026-07-17) — теперь отвечает через `context.bot.send_message
(chat_id=user_id, ...)`, если `query.message` нет (личный чат → `chat_id
== user_id`). Если где-то ещё в боте появится ветка, реально достижимая с
кнопки этого сообщения — тот же паттерн обязателен.

**«Свои пожелания» (input_hint) в 1-тапе** — второй формат callback_data:
`pl_usen_{cat_idx}_{item_idx}_{note_b64}`, где `note_b64` — `base64url`
(без `=`) от текста пожелания, **обрезанного до ~30 байт сырого UTF-8 ДО
кодирования** (жёсткий лимит Telegram — 64 байта на весь callback_data,
кириллица — 2 байта/символ). Пусто → как раньше, `pl_use_{cat_idx}_{item_idx}`
без note. Полное ТЗ фронту (кто и как кодирует, псевдокод) —
[docs/specs/2026-07-17_inline_note_passthrough.md](specs/2026-07-17_inline_note_passthrough.md).

Секреты: `BOT_TOKEN` заводится вторым секретом в Cloudflare Pages (тот же
токен, что в BotHost) — секретами занимается Аня, не бэкенд-сессия.

## Двух-референсные стили (`style_extract`, 2026-07-17)

Стили вроде «Образ с референса» (💄 Бьюти) ждут от юзера ДВА фото: первое —
лицо, второе — референс причёски/макияжа. Раньше оба фото уходили в
image-модель одним запросом, и она через раз путала, чьё лицо использовать
(нестабильность ~50/50, детали — docs/briefs/backend.md, P1 «Образ с
референса»). Решение — двухшаговый пайплайн на стороне бота:

1. Второе фото → text-only vision-вызов (Gemini), описывающий ТОЛЬКО причёску
   и макияж, без внешности/лица.
2. Генерация как обычный одно-референсный стиль: первое фото + текстовое
   описание из шага 1. Второе фото в image-модель не попадает вообще.

Флаг `style_extract: true` на item в `prompt_library.json` включает этот
пайплайн для конкретного стиля (бот резолвит его из PROMPT_LIBRARY по
`cat_idx`/`item_idx` — тот же путь резолва, что и у `title`/`upload_hint`,
работает во всех путях применения: обычный вебапп-payload, showcase (`shc_`),
инлайн-1-тап `pl_use_`/`pl_usen_`). Порядок загрузки фото юзером всё ещё
важен (первое — лицо, второе — стиль) — `upload_hint` должен явно об этом
предупреждать. Фронту от бота ничего не требуется, кроме проставления
флага на нужном item — вся логика извлечения на стороне бота
(`extract_style_description_from_reference`, `run_generation` в SirNike.py).
