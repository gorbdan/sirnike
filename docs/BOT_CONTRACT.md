# Контракт бот ↔ вебапп «Библиотека стилей»

Вебапп живёт в отдельном репо (Cloudflare Pages, https://sirnike.pages.dev).
Бот синкает `prompt_library.json` из вебаппа при старте — **source of truth = репо вебаппа**.
Парсер на стороне бота: `apply_webapp_prompt_payload_v2` (SirNike.py, ~строка 3096).

## prompt_library.json

Массив категорий:

```json
[
  {
    "title": "Название категории",
    "emoji": "🎬",
    "items": [
      {
        "title": "Название стиля",        // у ФОТО-стилей отсутствует НАМЕРЕННО — не дописывать!
        "prompt": "полный промт",
        "type": "video",                   // отсутствует = фото
        "video_url": "...", "poster_url": "...",   // для видео
        "example_url": "...",              // для фото
        "image_prompt": "...",             // опц.: промт стилизации кадра перед видео
        "description": "описание для карточки",
        "upload_hint": "Фото лица + 5 фото одежды", // что загрузить юзеру
        "input_hint": "Опиши свои пожелания (необязательно)", // опц.: показывает в модалке текстовое поле,
                                                                // введённый текст уходит в payload как note/n
        "style_extract": true,                             // опц.: см. раздел «Двух-референсные стили» ниже
        "added_at": "ISO-дата"
      }
    ]
  }
]
```

⚠️ У фото-стилей `title` отсутствует намеренно (решение владельца, карточки фото
без подписей — НЕ дописывать). Бот берёт fallback-лейбл (`_showcase_item_label`)
по `cat_idx`/`item_idx`, которые вебапп шлёт в каждом payload. У видео `title` заполняется.

**Исключение (2026-07-15, решение владельца):** у категории **💄 Бьюти** `title`
заполнен у всех фото-стилей — по её отдельной просьбе, специально для этой
категории. Остальные категории — правило «без title» остаётся в силе.

## Payload web_app_data (вебапп → бот)

JSON строкой. Полные и короткие ключи равнозначны:

| Поле | Кратко | Значение |
|---|---|---|
| `action` | `a` | `set_prompt` \| `set_video_prompt` \| `set_prompt_ref` \| `set_video_prompt_ref` \| `topup` \| `board_refs` (+ алиасы `apply_prompt`, `use_prompt`, `apply_template`, `connect_board`, `br`…) |
| `title` | `t` | название стиля (показывается юзеру); для `board_refs` — название доски |
| `prompt` | `p` | полный промт |
| `image_prompt` | — | опц., промт стилизации кадра для видео |
| `cat_idx` | `ci` | fallback: индексы вместо промта, |
| `item_idx` | `ii` | если payload не влезает — бот резолвит промт локально |
| `note` | `n` | опц., свободный текст юзера из поля `input_hint` — бот дописывает его в конец промта после резолва (см. `apply_webapp_prompt_payload_v2`), пусто = промт уходит как есть |
| `board_refs` | `br` | доски (MVP), см. ниже — массив уже захостенных на imgbb URL фото доски |

Правила:
- Payload > лимита Telegram → слать только `ci`/`ii` + `a` (+ `note`, если заполнен), без `p`.
- `topup` открывает у бота экран пополнения.
- Менять формат payload или структуру JSON — только синхронно с правкой парсера в боте
  (бриф бэкенду в `docs/briefs/backend.md` в репо бота).

## Доски (mood-борды), MVP (2026-08-09)

По [docs/specs/2026-08-09_mood_boards.md](specs/2026-08-09_mood_boards.md). Доски
целиком хранятся на стороне вебаппа (localStorage) — **бот их не хранит**, только
принимает уже захостенные фото активной доски и кладёт их в свой буфер референсов
для следующей генерации. Никакого AI-анализа стиля на MVP-этапе (это Full,
отдельная будущая задача).

Payload при «✅ Сделать активной и продолжить» (Экран 2 спеки), тем же
механизмом (`tg.sendData` / `answerWebAppQuery`), что и обычное «Использовать»:

```json
{"action": "board_refs", "title": "Вечерний гламур", "board_refs": ["https://i.ibb.co/...", "..."]}
```

- `board_refs`/`br` — массив URL (уже захостенных на imgbb той же Cloudflare
  Function, что используется для Студии нейромультиков) — до 10 в самой доске,
  бот берёт **первые 8** (существующий потолок референсов на одну генерацию,
  `_append_reference_url` в SirNike.py — общий код с ручной загрузкой фото), остальные
  молча не идут в референс (не баг).
- `title`/`t` — название доски (в этом экшене НЕ название стиля).
- Бот отвечает в чат подтверждением (текст зафиксирован спекой дословно) +
  кнопкой «📚 Библиотека стилей» — дальше юзер идёт по обычному пути выбора
  стиля, применение стиля НЕ трогает фото доски (они уже в буфере референсов).
- `note`/`n` в этом действии не используется и не читается ботом — не путать
  с «свои пожелания» юзера к конкретному стилю (другая сущность,
  [docs/specs/2026-07-17_note_override_weak.md](specs/2026-07-17_note_override_weak.md)).
- Реализация на стороне бота: `apply_webapp_board_refs_payload` (SirNike.py).

## Доски — Full, AI-анализ стиля (2026-08-09)

Отдельное действие, НЕ путать с `board_refs` выше — вебапп шлёт его от 2 фото
в доске (кнопка «✨ Понять мой стиль»), реализовано и задеплоено на стороне
вебаппа. Полное ТЗ (обработчик, формат сообщения-подтверждения, где и как
описание подмешивается в промт КАЖДОЙ генерации, отключение, обработка
ошибок): [docs/specs/2026-08-09_mood_boards_full.md](specs/2026-08-09_mood_boards_full.md).

```json
{"action": "board_style_analyze", "board_id": "<uuid вебаппа>", "title": "<имя доски>", "board_refs": ["<url>", "..."]}
```

- Короткий алиас действия — `bsa`. `board_id` — стабильный локальный UUID
  доски (используется ботом для последующих callback'ов «Всё верно»/
  «Поправить»/«Отключить» в чате — сам обмен текстом описания живёт целиком
  в чате бота, НЕ в вебаппе, у бота нет публичного HTTP для синхронного
  ответа обратно в мини-апп).
- `board_refs` — до 10 фото (весь состав доски, не 8 — потолок в 8 относится
  только к референсам ГЕНЕРАЦИИ), бот берёт до 6 для vision-анализа.
- Тот же payload-канал и защита от инлайн-входа, что у `board_refs`.
- Реализация на стороне бота: `apply_webapp_board_style_analyze_payload` (SirNike.py).

## Инлайн-путь «Использовать» в 1 тап (Cloudflare Function, вариант B)

Решение по [docs/specs/2026-07-15_webapp_inline_1tap.md](specs/2026-07-15_webapp_inline_1tap.md)
принято 2026-07-16: **вариант B**. `sendData()` работает только для вебаппа,
открытого с reply-клавиатуры (`persistent_menu_kb`) — это НЕ меняется,
остаётся основным путём. Для вебаппа, открытого с ИНЛАЙН-кнопки (`main_menu_kb`,
`result_actions_kb` — там, где сейчас 2-таповый обход через `pl_open_webapp`),
добавляется отдельный путь через `answerWebAppQuery`:

1. Вебапп открыт с инлайн-кнопки → `tg.initDataUnsafe.query_id` присутствует.
2. Тап «Использовать» → вместо `tg.sendData()` вебапп шлёт `POST` на Cloudflare
   Function (репо вебаппа, `/functions/answer-webapp-query` или аналогично —
   путь фронтенд выбирает сам) с телом:
   ```json
   {"init_data": "<tg.initData как есть>", "cat_idx": 3, "item_idx": 7, "note": ""}
   ```
3. Function проверяет HMAC-подпись `init_data` секретом `BOT_TOKEN` (алгоритм
   — офиц. доки Telegram, "Validating data received via the Mini App"), достаёт
   `query_id`, отклоняет запрос при невалидной подписи.
4. Function вызывает Telegram Bot API напрямую (`fetch`, без SDK):
   ```
   POST https://api.telegram.org/bot<BOT_TOKEN>/answerWebAppQuery
   {
     "web_app_query_id": "<query_id из initData>",
     "result": {
       "type": "article",
       "id": "pl_use_3_7",
       "title": "Использовать стиль",
       "input_message_content": {"message_text": "📚 Стиль подобран — жми ниже 👇"},
       "reply_markup": {"inline_keyboard": [[
         {"text": "🚀 Использовать", "callback_data": "pl_use_3_7"}
       ]]}
     }
   }
   ```
5. Telegram сам вставляет это сообщение в чат юзера с ботом. Тап по кнопке —
   обычный `callback_query` с `callback_data=pl_use_{cat_idx}_{item_idx}`,
   бот обрабатывает его существующим хэндлером `button_handler` → ветка
   `pl_use_` (SirNike.py) — тот же код, что у инлайн-каталога библиотеки
   внутри бота. Дублировать логику применения стиля не пришлось.
6. Вебапп после успешного ответа Function вызывает `tg.close()`. При сетевой
   ошибке — показать тост, `tg.close()` не звать (см. критерий приёмки в спеке).

⚠️ **У кнопки под answerWebAppQuery-сообщением `query.message` в боте
ВСЕГДА `None`** (Bot API: у `CallbackQuery` ровно одно из полей
`message`/`inline_message_id`, для инлайн-сообщений — второе). Раньше
`pl_use_` отвечал через `query.message.reply_text(...)` и падал молча
(живой баг 2026-07-17) — теперь отвечает через `context.bot.send_message
(chat_id=user_id, ...)`, если `query.message` нет (личный чат → `chat_id
== user_id`). Если где-то ещё в боте появится ветка, реально достижимая с
кнопки этого сообщения — тот же паттерн обязателен.

**«Свои пожелания» (input_hint) в 1-тапе** — второй формат callback_data:
`pl_usen_{cat_idx}_{item_idx}_{note_b64}`, где `note_b64` — `base64url`
(без `=`) от текста пожелания, **обрезанного до ~30 байт сырого UTF-8 ДО
кодирования** (жёсткий лимит Telegram — 64 байта на весь callback_data,
кириллица — 2 байта/символ). Пусто → как раньше, `pl_use_{cat_idx}_{item_idx}`
без note. Полное ТЗ фронту (кто и как кодирует, псевдокод) —
[docs/specs/2026-07-17_inline_note_passthrough.md](specs/2026-07-17_inline_note_passthrough.md).

Секреты: `BOT_TOKEN` заводится вторым секретом в Cloudflare Pages (тот же
токен, что в BotHost) — секретами занимается Аня, не бэкенд-сессия.

## Двух-референсные стили (`style_extract`, 2026-07-17)

Стили вроде «Образ с референса» (💄 Бьюти) ждут от юзера ДВА фото: первое —
лицо, второе — референс причёски/макияжа. Раньше оба фото уходили в
image-модель одним запросом, и она через раз путала, чьё лицо использовать
(нестабильность ~50/50, детали — docs/briefs/backend.md, P1 «Образ с
референса»). Решение — двухшаговый пайплайн на стороне бота:

1. Второе фото → text-only vision-вызов (Gemini), описывающий ТОЛЬКО причёску
   и макияж, без внешности/лица.
2. Генерация как обычный одно-референсный стиль: первое фото + текстовое
   описание из шага 1. Второе фото в image-модель не попадает вообще.

Флаг `style_extract: true` на item в `prompt_library.json` включает этот
пайплайн для конкретного стиля (бот резолвит его из PROMPT_LIBRARY по
`cat_idx`/`item_idx` — тот же путь резолва, что и у `title`/`upload_hint`,
работает во всех путях применения: обычный вебапп-payload, showcase (`shc_`),
инлайн-1-тап `pl_use_`/`pl_usen_`). Порядок загрузки фото юзером всё ещё
важен (первое — лицо, второе — стиль) — `upload_hint` должен явно об этом
предупреждать. Фронту от бота ничего не требуется, кроме проставления
флага на нужном item — вся логика извлечения на стороне бота
(`extract_style_description_from_reference`, `run_generation` в SirNike.py).

## Хаб генерации — Конструкторы видео/Midjourney/Аватара/фото (2026-08-13, Full)

По [docs/specs/2026-08-13_webapp_generation_hub.md](specs/2026-08-13_webapp_generation_hub.md),
[docs/specs/2026-08-13_webapp_generation_hub_navigation_full.md](specs/2026-08-13_webapp_generation_hub_navigation_full.md)
и [docs/specs/2026-08-14_menu_simplification_and_enhance_constructor.md](specs/2026-08-14_menu_simplification_and_enhance_constructor.md).
Заменяет цепочку «пикер модели → панель настроек → фото по одному» одним
экраном вебаппа-конструктором на продукт (`constructor.js`/
`mj_constructor.js`/`avatar_constructor.js`/`photo_constructor.js`/
`enhance_constructor.js`, все — в репо вебаппа) + одной карточкой
подтверждения в чате. Пять независимых kill-switch'ей
(`VIDEO_CONSTRUCTOR_ENABLED`/`MIDJOURNEY_CONSTRUCTOR_ENABLED`/
`AVATAR_CONSTRUCTOR_ENABLED`/`PHOTO_CONSTRUCTOR_ENABLED`/
`ENHANCE_CONSTRUCTOR_ENABLED`, все выключены по умолчанию) — можно включать
по одному продукту, не всё сразу; при `False` входы ведут на старый
чат-флоу без единого изменения (для `enhance` — на ручной флоу
`_cb_enhance_photo`, кнопка «🖼️ Улучшить фото»).

Единый диспетчер на стороне бота: `apply_webapp_generation_payload` в
SirNike.py резолвит `payload["product"]` в `_apply_webapp_generation_video`/
`_apply_webapp_generation_midjourney`/`_apply_webapp_generation_avatar`/
`_apply_webapp_generation_photo`/`_apply_webapp_generation_enhance` —
каждый со своим kill-switch'ем, своим резолвом в `UserState` (теми же
полями, что заполняет сегодняшний чат-флоу) и своей карточкой
подтверждения с УЖЕ СУЩЕСТВУЮЩЕЙ кнопкой запуска (`video_start`/
`mj_generate`/`avatar_gen_start`/`generate`) — ноль нового кода в
биллинге/очереди/доставке результата. `enhance` — единственный продукт,
где карточка подтверждения НЕ новый текст, а прямой вызов существующих
`photo_draft_text`/`photo_draft_kb` (та же пара функций, что завершает
сегодняшний ручной флоу `_cb_enhance_photo` после присылки фото).

### Вход: `cfg` в персональном URL (бот → вебапп), только видео

У бота нет публичного HTTP — единственный канал передать вебаппу список
активных видео-моделей/форматов/качества/цен — параметр `cfg` в персональном
URL вебаппа, добавляется автоматически функцией `get_prompt_webapp_url`, пока
`VIDEO_CONSTRUCTOR_ENABLED` включён (Midjourney/Аватар/фото своей тяжёлой
`cfg`-таблицы не имеют — там нечего пробрасывать, кроме самого факта, что
конструктор включён, см. `&features=` ниже). `tab=video_constructor`
(SNAKE_CASE — именно так, ровно эту строку `constructor.js` сверяет из
query-параметра; `videoConstructor`, camelCase, это ВНУТРЕННЕЕ имя экрана
для `switchTab()`, НЕ значение параметра URL) переключает вебапп сразу на
экран Конструктора видео.

`cfg` — `base64url(JSON)` без паддинга (`get_video_constructor_config()` в
SirNike.py). Схема СВЕРЕНА с реальным `parseCfgFromUrl`/`FALLBACK_CFG`/
`vcModelFromCfgEntry` в `constructor.js` (репо вебаппа, уже смёржено) —
**менять эту форму можно только синхронно с правкой `parseCfgFromUrl`
там**:

```json
{
  "video_models": [
    {
      "code": "seedance2",
      "label": "Seedance 2",
      "blurb": "максимум качества и движения, наш выбор",
      "aspects": ["16:9", "9:16", "1:1", "4:3"],
      "modes": ["480p", "720p", "1080p"],
      "durations": [5, 10, 15],
      "face_grid": true,
      "prices": {
        "480p": {"5": 15, "10": 28, "15": 40},
        "720p": {"5": 20, "10": 45, "15": 65},
        "1080p": {"5": 30, "10": 60, "15": 85}
      }
    },
    {
      "code": "wan27",
      "label": "Wan 2.7 (Alibaba) 🆕",
      "blurb": "живая мимика и жесты",
      "aspects": ["16:9", "9:16"],
      "modes": ["480p", "720p", "1080p"],
      "durations": [5, 10],
      "prices": {
        "480p": {"5": 18, "10": 32}, "720p": {"5": 24, "10": 44}, "1080p": {"5": 32, "10": 58}
      }
    }
  ]
}
```

Правила:
- Корневой ключ — ровно `video_models` (НЕ `models`), без обёртки
  `default_model` — дефолт конструктора = первая модель списка, а первой
  всегда кладётся `seedance2` (единственная модель без фичефлага — включена,
  пока `SEEDANCE_ENABLED` вообще включён на уровне продукта). Порядок
  фиксирован: seedance2 → seedance2_fast → kling3 → veo31 → wan27 →
  gemini_omni → seedance25; в списке — только модели, у которых
  соответствующий фичефлаг включён (`SEEDANCE_FAST_ENABLED`/`KLING3_ENABLED`/
  `VEO31_ENABLED`/`WAN27_ENABLED`/`GEMINI_OMNI_ENABLED`/`SEEDANCE25_ENABLED`).
- Поля модели — `code`/`label`/`blurb`/`aspects`/`modes`/`durations`/
  `face_grid`/`prices` (НЕ `id`/`formats`/`quality`/`badge` — та форма была
  ранним черновиком спеки и не совпадает с тем, что реально парсит
  `constructor.js`). `label` уже включает суффикс/эмодзи-бейдж строкой
  (`get_video_model_label` — «Seedance 2 Fast (бета)», «Kling 3.0 🆕» и т.п.),
  отдельного поля `badge` нет.
  `face_grid` — булево, опускается (не `false`), если модель детектор лиц не
  поддерживает.
- `modes` — реальные внутренние режимы модели (`get_seedance_mode_options`:
  `["480p","720p","1080p"]`/`["720p","1080p"]`/`["720p"]`/`["480p","720p"]`),
  может быть из одного элемента (тогда вебапп не показывает тумблер
  «Качество» — `constructor.js` включает тумблер по признаку `modes.includes
  ("480p")`). Про то, что бэкенд реально понимает из `payload.quality` —
  ТОЛЬКО `"fast"` (маппится на `modes[0]`, самый лёгкий доступный) и
  всё остальное, включая `"pro"` (маппится на `modes[-1]`, самый качественный
  доступный) — см. `resolve_webapp_video_quality` в SirNike.py.
  Wan 2.7 — обычная дискретная таблица длительностей/режимов, как у всех
  моделей (НЕ `{"custom":[min,max]}`/`{"per_second": N}` — этот вариант
  был в раннем черновике, реальный `constructor.js` его не парсит).
- `prices` — вложены по РЕАЛЬНОМУ значению режима (`"480p"`/`"720p"`/
  `"1080p"`, ключ `"default"`, если у модели `modes` пуст), НЕ по `"pro"`/
  `"fast"` — вебапп сам резолвит нужный бакет через `vcPriceBucketKey`
  (см. `constructor.js`). Цифры — уже посчитаны `calc_seedance_cost`/
  `get_video_model_cost_per_second` на момент открытия Mini App, для живого
  пересчёта в вебаппе. **Финальная цена в карточке подтверждения в чате
  всегда пересчитывается бэкендом заново** (не из `cfg`, не из присланного
  payload) — если цены разошлись, юзер видит актуальную, без сюрпризов при
  списании.

### `&features=` в персональном URL (бот → вебапп, все продукты)

Отдельно от `cfg` (только видео, тяжёлая таблица цен) — компактный булев
флаг-набор, ВСЕГДА проброшен в `get_prompt_webapp_url` вне зависимости от
`VIDEO_CONSTRUCTOR_ENABLED`, экран «Создать» (единая навигация) использует
его, чтобы скрывать плитки продуктов, конструктор которых ещё не включён:

```json
{"video": false, "midjourney": true, "avatar": false, "photo": true, "enhance": false}
```

### Payload при «🚀 Продолжить в чат» (вебапп → бот)

Действие `start_generation` (короткий алиас `sg`), тем же каналом
(`tg.sendData`), что и остальные действия — диспетчеризуется из
`apply_webapp_prompt_payload_v2` в `apply_webapp_generation_payload`
(SirNike.py), которая по полю `product` роняет payload дальше в
продукт-специфичный резолвер. Пример для видео (`buildStartGenerationPayload`
в `constructor.js`) — **полными ключами**, без сокращений (короткие алиасы
`pr`/`vm`/`ar`/`q`/`d`/`fg`/`p`/`r`/`bi` тоже поддержаны парсером на
будущее/для других клиентов):

```json
{
  "action": "start_generation",
  "product": "video",
  "video_model": "seedance2",
  "aspect": "9:16",
  "quality": "pro",
  "duration": 10,
  "face_grid": true,
  "description": "Кот танцует брейк-данс на кухне",
  "refs": ["https://i.ibb.co/...", "https://i.ibb.co/..."],
  "board_id": "uuid-доски-если-активна"
}
```

| Поле | Кратко | Значение |
|---|---|---|
| `product` | `pr` | `video` \| `midjourney` \| `avatar` \| `photo` \| `enhance` — остальные значения получают честное «скоро появится» |
| `video_model` | `vm` | `seedance2` \| `seedance2_fast` \| `kling3` \| `veo31` \| `wan27` \| `gemini_omni` \| `seedance25` |
| `aspect` | `ar` | `16:9` \| `9:16` \| `1:1` \| `4:3` (набор сужен по модели — см. `get_video_aspect_options`) |
| `quality` | `q` | `pro` \| `fast` — опц., только для моделей с несколькими `modes` в `cfg` |
| `duration` | `d` | число секунд — клампится в границы модели (`normalize_seedance_duration`) |
| `face_grid` | `fg` | `true`/`false` — опц., только Seedance 2 / 2 Fast |
| `description` | `p` | свободный текст юзера (для `video`/`midjourney`/`photo`) |
| `cat_idx`/`item_idx` | `ci`/`ii` | опц. — если описание пришло из библиотечного стиля (видео), бот резолвит `description` из PROMPT_LIBRARY по индексам, присланный текст игнорируется (тот же принцип, что `apply_webapp_prompt_payload_v2`) |
| `refs` | `r` | массив уже захостенных URL (imgbb/студийный аплоадер); видео — берёт первые `MAX_SEEDANCE_IMAGE_REFERENCES` (9), Midjourney — только первый (один референс), Аватар — первые `MAX_AVATAR_PHOTOS`, фото — первые 8, `enhance` — ровно первый (ровно 1 фото по продукту, лишние не ошибка, просто игнорируются) |
| `board_id` | `bi` | опц., чисто информационное — не меняет обработку `refs` |
| `avatar_type` | `at` | только `product=avatar`: `female` \| `male` \| `child`, неизвестное значение → `female` |
| `image_model` | `im` | только `product=photo`: `gpt5` (требует `GPT5_IMAGE_ENABLED`) \| иначе `gemini` |

Правила:
- **Серверная валидация фичефлагов ОБЯЗАТЕЛЬНА**: если `video_model`
  выключен на момент получения payload (устаревший кэш вебаппа у юзера) —
  бот НЕ падает и не игнорирует молча, откатывает на `seedance2` и
  предупреждает текстом («модель сейчас недоступна»), карточка
  подтверждения показывается с дефолтной моделью.
- Нет описания И нет фото/референсов — бот не показывает карточку, просит
  вернуться в конструктор и добавить хоть что-то (то же правило, что
  «кнопка есть ⇔ действие возможно» у `video_kb`).
- `product` вне пяти поддержанных — честное сообщение «не поддержан»,
  без побочных эффектов на state.
- `enhance` без `refs` (юзер не добавил фото) — бот не показывает карточку,
  просит вернуться в конструктор и добавить фото (тот же принцип, что у
  «нет описания И нет фото/референсов» выше, но для `enhance` фото —
  единственное обязательное поле, текстовых полей у экрана нет вообще).

### Экран подтверждения (бот → чат)

Одно сообщение вместо сегодняшних 2-3 (пикер + панель + фото отдельными
сообщениями). Формат для видео (`build_video_generation_confirm_text`,
поля показываются только если применимы/непусты):

```
🎬 Готово к запуску

Модель: Seedance 2 — максимум качества и движения, наш выбор
Формат: 9:16 (вертикаль, Reels)
Качество: Pro
Длительность: 10с
Детектор лиц: вкл 🟢 (защита от отказа модерации)
Фото: 3 шт.
Описание: есть

Стоимость: 45 🍇
```

Кнопки — одинаковый паттерн для четырёх продуктов (video/midjourney/avatar/
photo): «🚀 Запустить видео»/«🚀 Сгенерировать»/«🚀 Сгенерировать
аватар»/«🚀 Запустить генерацию» — переиспользует ровно существующий
callback (`video_start`/`mj_generate`/`avatar_gen_start`/`generate`, ноль
нового кода в биллинге/очереди/доставке результата); «✏️ Изменить» —
открывает конструктор заново персональным URL `&prefill=`
(`constructor_prefill_url`/`build_generation_prefill` в SirNike.py) С
СОХРАНЁННЫМ ЧЕРНОВИКОМ. `enhance` — исключение: карточка ЦЕЛИКОМ
переиспользует `photo_draft_text`/`photo_draft_kb` (та же карточка, что у
сегодняшнего ручного флоу «Улучшить фото» после присылки фото), а не
собственный текст/набор кнопок — там уже есть «🚀 Запустить генерацию»
(`generate`) и «✏️ Изменить» ведёт на `photo_draft_kb`, не на
`constructor_prefill_url`.

Персональный URL для `enhance` (кнопка-фолбэк при пустых `refs`, см.
`enhance_constructor_kb`) — `&tab=enhance_constructor` (SNAKE_CASE, тот же
принцип, что `tab=video_constructor`/`tab=avatar_constructor`/
`tab=photo_constructor` выше). У остальных четырёх продуктов `&prefill=`
(сериализует текущий `UserState` в ту же форму полей, что вебапп сам
присылает в `start_generation`/`sg`) — Full, заменило MVP-кнопку
«🔁 Начать заново» (пустой конструктор без черновика).

## Меню бота (2026-08-14, радикальное упрощение)

По [docs/specs/2026-08-14_menu_simplification_and_enhance_constructor.md](specs/2026-08-14_menu_simplification_and_enhance_constructor.md).
Продуктовое решение Ани: раз Хаб генерации в вебаппе теперь закрывает ВСЕ
продукты (Фото/Видео/Аватар/Midjourney/Улучшить фото/Доски/Студия) одним
экраном с единой навигацией — держать те же продукты ЕЩЁ РАЗ отдельными
чат-флоу в меню бота избыточно. И `main_menu_kb` (инлайн), и
`persistent_menu_kb` (reply-клавиатура под полем ввода) сжаты до ровно
3 кнопок, тексты буква в букву синхронны между обоими меню:

```
[ 📚 Библиотека и генерация ]
[ 🐞 Баг-баунти ]  [ 💰 Баланс ]
```

Это значит для вебаппа: **кнопка «📚 Библиотека и генерация»
(`MENU_BTN_LIBRARY` в SirNike.py) — теперь единственная штатная точка
входа во весь вебапп** из главного меню бота (помимо инлайн-кнопок на
карточках результата, deep-link'ов и `/start` — они не часть этой
задачи и не изменились). Она открывает вебапп **без форсированного
`&tab=library`** — юзер видит дефолтный экран вебаппа («Создать»), а не
сразу каталог стилей, потому что кнопка ведёт во ВЕСЬ хаб, не только в
библиотеку. Остальные 12 точек входа в вебапп по всему боту (карточка
фото-драфта, экран баланса, карточка результата, рассылки, промо,
подсказки после подключения доски и после устаревшей карточки стиля и
т.д.) — продолжают форсировать `&tab=library` (см. раздел про
`tab=video_constructor` выше, тот же приём) и НЕ затронуты этой задачей —
это осознанно разные сценарии: та кнопка целенаправленно ведёт в каталог,
эта — в хаб целиком.

Убраны из обоих меню как КНОПКИ (не как код — хендлеры
`_cb_menu_photo`/`_cb_menu_video`/`report_problem`/`open_ref`/
`show_help`/весь чат-флоу Midjourney/Аватара/Студии/Видео остаются в
SirNike.py рабочими, просто без входа с главного меню): «📸 Фото»,
«🎬 Видео», «🎁 Пригласить друга», «❓ Как пользоваться», «🚨 Проблема».

Для вебаппа это означает, что при разработке экрана «Создать» стоит
считать его единственной точкой входа для новых и возвращающихся юзеров
(кроме прямых ссылок на конкретный `tab=`) — навигация внутри вебаппа
(переключение между Библиотекой/Фото/Видео/Аватар/Midjourney/Улучшить
фото/Досками/Студией) теперь полностью на стороне вебаппа, бот больше не
предлагает альтернативных чат-путей туда.
