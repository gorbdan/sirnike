# ТЗ: канал доставки статистики для раздела «Топ-стили» в вебаппе

Автор: фронтенд-сессия. Адресат: бэкенд. Дополняет P2 из
[docs/briefs/frontend.md](../briefs/frontend.md) («Топ-стили» на главном
экране каталога).

## Проблема

Данные для «Топ-стили» реально есть: бот пишет каждое применение шаблона в
`template_usage_events` (db.py) и умеет их агрегировать —
`get_template_usage_counts(days=None)` уже возвращает
`{(category, item_title): count}`. Но вебапп — статика на Cloudflare Pages,
без доступа к БД бота. Нужен канал доставки чисел от бота к вебаппу.

## Почему не через прямой API-запрос из вебаппа

Вебапп уже синкает `prompt_library.json` как статический файл при деплое —
предлагаю тот же паттерн для статистики, а не заводить живой HTTP-эндпоинт
(лишняя поверхность, лишняя инфраструктура, обсуждали похожий компромисс в
[docs/specs/2026-07-15_webapp_inline_1tap.md](2026-07-15_webapp_inline_1tap.md)
для другой задачи — там она была оправдана нуждой в real-time ответе, здесь
статистика по определению не real-time, раз в день более чем достаточно).

## Предложение

1. Бот периодически (по крону/при старте, на ваше усмотрение) считает топ-N
   (например, топ-10) по `get_template_usage_counts(days=30)` — 30 дней, а не
   всё время, чтобы топ отражал актуальный тренд, а не стухшую популярность
   стиля, который был хитом в июне.
2. **Важно**: результат нужно резолвить в `cat_idx`/`item_idx` — АБСОЛЮТНЫЕ
   индексы в `PROMPT_LIBRARY`, не текстовые `category`/`item_title`. Бот уже
   умеет это (та же логика, что резолвит `_showcase_item_label` при записи
   события) — печатать индексы, а не строки, чтобы вебапп не занимался
   нечётким сопоставлением текста (ровно те баги с рассинхроном текста,
   что чинили в payload — см. `docs/specs/2026-07-12_webapp_payload.md`).
3. Публикует результат туда, откуда вебапп сможет его подтянуть — либо
   отдельным файлом `top_styles.json` рядом с `prompt_library.json` в репо
   вебаппа (коммитом от бота, если у него есть push-доступ туда), либо
   любым другим уже существующим у вас механизмом синка — вам решать, как
   технически проще на вашей стороне.

   Формат файла, который ждёт фронтенд:
   ```json
   [
     { "cat_idx": 13, "item_idx": 0, "uses_30d": 142 },
     { "cat_idx": 2, "item_idx": 3, "uses_30d": 98 }
   ]
   ```

## Что сделает фронтенд, когда файл появится

Подтянет `top_styles.json` так же, как `prompt_library.json` (`fetch` при
загрузке), резолвит `cat_idx`/`item_idx` в реальные items и отрисует раздел
«Топ-стили» вверху каталога. Если файла нет / он пуст / резолв индекса не
удался (например, отставание после переиндексации библиотеки) — раздел
просто не показывается, без ошибок (уже есть паттерн graceful-деградации
в коде вебаппа для похожих случаев).

## Критерий готовности

Файл `top_styles.json` появляется в репо вебаппа (или там, откуда фронтенд
сможет его забрать) и обновляется не реже раза в сутки. Формат — как в
примере выше. Согласовать точный механизм доставки (крон + git push /
что-то другое) — как вам удобнее технически, формат JSON — то, что
действительно важно зафиксировать заранее.
