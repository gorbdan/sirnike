# ТЗ: «свои пожелания» (input_hint) не доходят через инлайн-1-тап

Автор: бэкенд-сессия. Адресат: фронтенд (репо вебаппа). Контекст: живой тест
Ани нашёл регресс от фичи 1-тапа
([docs/specs/2026-07-15_webapp_inline_1tap.md](2026-07-15_webapp_inline_1tap.md)) —
поле «Опиши свои пожелания» (input_hint) в карточке стиля физически не может
доехать до бота, если вебапп открыт с инлайн-кнопки.

## Причина

Два независимых пути доставки выбора стиля от вебаппа к боту:

1. **sendData** (вебапп открыт с reply-клавиатуры, нижнее меню) — вебапп шлёт
   `Telegram.WebApp.sendData()` с полным JSON-payload: `action`, `cat_idx`,
   `item_idx`, и `note`/`n` (свободный текст из input_hint). Бот получает это
   как `message.web_app_data`, парсит весь payload — **note доезжает,
   работает как задумано.**
2. **answerWebAppQuery** (вебапп открыт с ИНЛАЙН-кнопки, 1-тап) — вебапп шлёт
   POST на Cloudflare Function с `{cat_idx, item_idx, note}`
   ([docs/BOT_CONTRACT.md](../BOT_CONTRACT.md#инлайн-путь-использовать-в-1-тап-cloudflare-function-вариант-b)),
   Function вызывает `answerWebAppQuery` с результатом — кнопкой
   `callback_data=pl_use_{cat_idx}_{item_idx}`. **В этом callback_data места
   для note никогда не было** — Function получает note в POST-теле, но
   никуда его не кладёт при формировании ответа Telegram.

Итог: юзер вписывает пожелание в карточку → открыто с инлайн-кнопки → тап
«Использовать» → пожелание молча теряется, применяется общий (дефолтный)
промт стиля.

## Фикс (бэкенд уже готов принимать; нужна правка Function)

Бот теперь понимает **второй** формат callback_data:
`pl_usen_{cat_idx}_{item_idx}_{note_b64}` — то же самое, что `pl_use_...`,
плюс note, закодированный `base64url` (без padding `=`, бэкенд сам
восстанавливает при декодировании).

**Когда слать какой формат:**
- Пусто/юзер ничего не вписал в input_hint → как и раньше, `pl_use_{cat}_{item}`.
- Есть note → `pl_usen_{cat}_{item}_{note_b64}`.

### ⚠️ Жёсткий лимит: 64 БАЙТА на весь callback_data (ограничение Telegram)

Это самое узкое место всей задачи. `answerWebAppQuery` с результатом, чей
`callback_data` превышает 64 байта, Telegram **отклонит целиком** — кнопка
«Использовать» вообще не появится у юзера, без объяснений. Бюджет на сам
note очень маленький:

- Служебная часть (`pl_usen_`, индексы, 2 подчёркивания) — обычно 12-16 байт.
- `base64` раздувает объём в 4/3 раза.
- Кириллица — **2 байта на символ** в UTF-8 (не 1!).

Практический бюджет: **обрезать note до ~30 байт СЫРОГО UTF-8 текста ДО
кодирования** (≈ 15 кириллических символов, чуть больше латиницей/цифрами) —
этого хватает на короткую фразу («каре, блонд», «синий фон») и держит общую
длину callback_data safely под 64 байтами с запасом на 2-3-значные индексы.
Обрезать **по границе символа**, не разрывая multi-byte UTF-8 (иначе на
бэкенде декодируется мусор в хвосте — не критично, бэкенд декодирует с
`errors="ignore"`, но лучше просто не резать посреди символа).

Если после обрезки note всё ещё даёт длинную фразу и это некомфортно —
приемлемый компромисс: короткое пожелание долетает как есть, длинное просто
обрезается молча (тот же принцип, что уже применён к обрезке payload в
sendData-пути, см. `docs/specs/2026-07-12_webapp_payload.md`). Не нужно
показывать юзеру ошибку — просто truncate.

### Псевдокод (JS)

```js
function encodeNoteForCallback(note) {
  if (!note) return "";
  const bytes = new TextEncoder().encode(note);
  let truncated = bytes;
  if (bytes.length > 30) {
    // обрезать по границе UTF-8 символа
    let end = 30;
    while (end > 0 && (bytes[end] & 0xc0) === 0x80) end--;
    truncated = bytes.slice(0, end);
  }
  const b64 = btoa(String.fromCharCode(...truncated))
    .replaceAll("+", "-").replaceAll("/", "_").replace(/=+$/, "");
  return b64;
}

// при формировании результата answerWebAppQuery в Cloudflare Function:
const noteB64 = encodeNoteForCallback(note);
const callbackData = noteB64
  ? `pl_usen_${catIdx}_${itemIdx}_${noteB64}`
  : `pl_use_${catIdx}_${itemIdx}`;
```

(Кодирование можно сделать и на клиенте перед POST, и в самой Function —
не принципиально, где именно; главное — использовать `pl_usen_` только
когда note непустой, и `pl_use_` в остальных случаях, как сейчас.)

## Что уже сделано на бэкенде (не нужно дублировать)

- `button_handler` в SirNike.py понимает оба префикса (`pl_use_`/`pl_usen_`),
  декодирует `base64url`, дописывает note к промту (та же логика, что в
  sendData-пути — `"User's specific wish (follow this instead of the generic
  description above): {note}"`).
- Подтверждение в чате («Готово ✨ Стиль применён...») теперь показывает
  «✍️ Учла твои пожелания: «{note}»» ВМЕСТО статичного «Что получится:
  {дефолтное описание}» — раз юзер попросил другое, канцелярское описание
  из библиотеки печатать нечестно (тот же фикс применён и к sendData-пути).
- Регрессионные тесты 9.19–9.20 в test_new_features.py.

## Критерий готовности

Открыть карточку стиля с `input_hint` через инлайн-кнопку (главное меню/
под результатом) → вписать короткое пожелание (≤15 кириллических символов)
→ «Использовать» → в чате «✍️ Учла твои пожелания: «...»» с текстом ровно
тем, что вписал юзер (без обрезки на коротких фразах) → генерация
действительно учитывает пожелание, а не дефолтное описание стиля.
