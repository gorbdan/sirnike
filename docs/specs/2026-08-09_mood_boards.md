Дата: 2026-08-09. Приоритет: P0 (партнёрская интеграция с блогером, дедлайн «сейчас»).
Источник: живая цитата блогера-партнёра (передана маркетологом, полный разбор в

## Технические рамки (важно — определяет архитектуру всей спеки)

Фото-провайдеры бота (Zveno/EvoLink/MashaGPT, `config.py`) — это НЕ
LoRA/fine-tuning платформы, у них нет API «дообучить модель на фото юзера».
Реальные строительные блоки, которые есть в проде уже сегодня:

1. **Промт-текст.** Стиль = текст, автоматически добавляемый к запросу
   (`prompt_library.json`, `apply_webapp_prompt_payload_v2`).
2. **Фото-референсы в сам вызов генерации.** `state.references` уже
   поддерживает до 8 фото на одну генерацию (SirNike.py:3596-3599), видео —
   до 9 (`MAX_SEEDANCE_IMAGE_REFERENCES`, config.py:177-182). Работает для
   аватара, «Оживить в видео», Kling/Veo мульти-референсов.
3. **Vision-анализ фото → текстовое описание, вплетаемое в промт.**
   Уже в проде: `extract_style_description_from_reference`
   (SirNike.py:4437) — второе фото у стиля «Образ с референса» (💄 Бьюти,
   `style_extract: true`) уходит в Gemini/Zveno vision-вызовом, получает
   текстовое описание причёски/макияжа, это описание подмешивается в промт
   вместо самого фото.

«Персонализация» технически возможна ТОЛЬКО как комбинация (1)+(2)+(3) —
никакого дообучения модели. Это ограничение заложено в архитектуру ниже
явно, а не спрятано за красивым UI, который physически не может работать.

## Принцип решения

Три пункта Midjourney ложатся на бота так:

| Midjourney | Сырник |
|---|---|
| Вкладка со стилем | **Уже есть** — Библиотека стилей (категории, поиск, избранное). Нового экрана не нужно, см. раздел «Сверка» ниже. |
| Mood-борды | **Новая сущность «Доска»** — именованная коллекция фото, несколько досок, переключение между ними. |
| Персонализация | **Слой поверх досок**: MVP — доска = фото-референсы для генерации (без AI). Full — доска ещё и авто-описывает себя текстом через vision и подмешивает его в промт. |

Доска — не отдельный продукт и не замена библиотеки стилей, а **параллельный
слой поверх существующего флоу**: подключается ДО выбора стиля (юзер сначала
готовит референсы), действует ВМЕСТЕ со стилем (не вместо — выбор стиля не
меняется ни на шаг). Юзер, который не трогает доски, не видит вообще никаких
изменений в привычном пути, кроме одной новой строки в каталоге.

## Нейминг (ЦА не знает слова «мудборд»)

Пользовательское название — **«Доска»** (метафора Pinterest-досок, знакома
широкой аудитории; сегмент 2 из MARKETING_PLAN.md — бьюти-мастера/SMM — сам
использует триггер «быстро создать moodboard», так что термин не чужой). Ни
в одном пользовательском тексте не используются слова «промт», «референс»,
«модель» — только «фото» и «стиль».

## Флоу: было → стало

**Было** (сегодня):
1. «📚 Библиотека стилей» → открывается каталог.
2. Категории/поиск → карточка стиля → модалка («Что загрузить», «📋
   Скопировать» / «🚀 Использовать»).
3. «Использовать» → бот получает промт, просит фото → юзер грузит фото →
   генерация.

**Стало** (с досками, MVP; шаги 1-2 — новые, шаги 3-5 — прежние с одной
припиской):
1. *(Необязательно, до похода в библиотеку)* юзер создаёт доску, собирает
   3-8 фото, жмёт «✅ Сделать активной и продолжить».
2. Бот в чате подтверждает: доска подключена, фото загружены как референс,
   предлагает кнопку «📚 Библиотека стилей».
3. Юзер листает каталог как раньше — единственная разница: сверху виден
   баннер активной доски, в карточке стиля — информационная строка «🖼️ С
   доски «Название» тоже подмешается».
4. «Использовать» → бот генерирует, используя ОБА источника: фото с доски
   (референс) + промт выбранного стиля — юзеру НЕ нужно повторно грузить
   фото, доска их уже передала.
5. Если юзер вообще не создавал доски — путь идентичен «было», ноль
   изменений.

## Экран 1 — Каталог, главная (webapp)

**Стало**: новая горизонтальная секция «🖼️ Мои доски», по паттерну уже
существующих секций каталога («Новинки», будущая «Топ-стили» — P2 в
`docs/briefs/frontend.md`). Позиция — рядом с «Новинки», до списка категорий
(точный порядок — на усмотрение фронтенда, критично только не прятать её
глубоко за скроллом).

- 0 досок у юзера: секция состоит из ОДНОЙ плитки «+ Новая доска» с
  подписью под ней «Собери фото для своего стиля».
- ≥1 доска: плитки досок (обложка — коллаж из фото доски или иконка-заглушка
  «🖼️» на пустой), под каждой — название доски; если доска активна — на
  плитке круглый бейдж-галочка. Последняя плитка в ряду — всегда «+ Новая
  доска». До 5 досок (лимит MVP, см. «Лимиты») — все умещаются в один ряд
  без экрана «показать все».

Тап по плитке доски → Экран 2. Тап «+ Новая доска» → модалка ниже.

**Если активна доска** — поверх каталога (на ВСЕХ экранах каталога: главная,
категория, поиск), закреплённый баннер под шапкой:

```
🖼️ Доска «Вечерний гламур» активна · [Сменить] · [Отключить]
```

«Отключить» — мгновенно снимает активность (клиентское состояние,
localStorage — см. «Архитектура MVP»), доска и её фото никуда не пропадают.
«Сменить» — открывает секцию «Мои доски».

## Экран 1a — Модалка «Новая доска»

```
Заголовок: Новая доска
Поле:      [текстовое, placeholder «Например, «Вечерний гламур»»]
Кнопки:    Создать | Отмена
```

«Создать» неактивна, пока поле пустое. После создания — сразу переход на
Экран 2 (доска пустая, 0 фото).

## Экран 2 — Доска (просмотр/редактирование)

```
‹ Мои доски                              [название доски] ✏️    ⋮
```
- Название — тап по нему или по ✏️ включает инлайн-редактирование (Enter/
  клик вне поля — сохраняет).
- «⋮» — меню: «Переименовать» / «Удалить доску».

Под шапкой — статус-баннер:
- Доска НЕ активна: кнопка на всю ширину «Сделать доску активной».
- Доска активна: баннер «🖼️ Доска активна — фото из неё пойдут в следующую
  генерацию» + текстовая ссылка-кнопка «Отключить».

Тело экрана — сетка фото (квадратные превью). На каждом — крестик «×» в
углу для удаления (принцип: удаление фото — явное действие юзера на
конкретном объекте, не кнопка навигации).

**Пустая доска** (0 фото): иконка + текст «Пока пусто. Добавь несколько
фото — свои снимки или картинки-вдохновение.» + кнопка «📷 Добавить фото».

Нижняя закреплённая панель (доска с ≥1 фото):
- «📷 Добавить фото» — открывает выбор файла с устройства (тот же
  Cloudflare Function-загрузчик на imgbb, что уже сделан для Студии
  нейромультиков, docs/specs/2026-07-20_cartoon_studio.md — повторно
  используем, не строим заново). Дизейбл + тултип «Максимум 10 фото в
  доске» на лимите.
- Если доска ещё НЕ активна и в ней ≥1 фото — вторая, главная кнопка:
  «✅ Сделать активной и продолжить». Тап: доска становится активной,
  вебапп закрывается и уходит в чат бота ровно тем же payload-механизмом,
  что и сегодняшнее «Использовать» (`tg.sendData`/`answerWebAppQuery`), но
  с новым действием (см. «Технические заметки»).

**Переключение с одной активной доски на другую**: юзер открывает доску B,
пока активна A, жмёт «Сделать доску активной» — активной становится B,
подтверждение в чате бота явно называет замену (см. ниже), а не тихо
переписывает состояние.

## Экран 3 — Подтверждение в чате бота (после «Сделать активной и продолжить»)

Текст сообщения бота (первый раз или смена доски — формулировка одна и та
же, разница только в счётчике):

```
🖼️ Доска «Вечерний гламур» подключена — фото из неё будут использоваться
как референс (загружено 6/8).
Теперь выбери стиль в библиотеке 👇
```
Кнопка под сообщением: «📚 Библиотека стилей» (существующая, текст
`MENU_BTN_LIBRARY`, SirNike.py:1359 — переиспользуется дословно, новый текст
не придумываем).

Если в доске больше 8 фото — в референс уходят первые 8 (лимит на
одну генерацию, тот же, что уже действует для ручной загрузки, SirNike.py
`_refs_cap`), остальные фото доски остаются в ней для просмотра (и в Full-версии
участвуют в анализе стиля).

## Экран 4 — Карточка стиля в библиотеке, когда доска активна

Без изменений в кнопках («📋 Скопировать» / «🚀 Использовать» — тексты те
же). Добавляется одна информационная строка НАД блоком «Что загрузить»
(если он есть) или на его месте (если стиль не просит фото отдельно):

```
🖼️ С доски «Вечерний гламур» тоже подмешается
```

Строка не интерактивна — не создаёт скрытого состояния, только объясняет
уже видимое (баннер сверху экрана).

## Лимиты v1 (конфигурируемые)

- **До 5 досок на юзера** (по аналогии с `STUDIO_MAX_SCENES` — константа,
  предлагаемое имя `MOODBOARD_MAX_BOARDS`, дефолт 5).
- **До 10 фото в доске** (`MOODBOARD_MAX_PHOTOS_PER_BOARD`, дефолт 10) — из
  них в саму генерацию как референс уходит не больше 8 (существующий
  потолок референсов на фото-генерацию), остаток — про запас для Full-версии
  (AI-анализ смотрит на всю доску, не только на первые 8).
- Активная доска — **одна** одновременно (без мульти-подключения досок в
  один запрос — усложняет промт без явной пользы, отдельный кейс, если
  понадобится).

При достижении лимита — понятное сообщение («Максимум 10 фото в доске» /
аналогично для досок), не тихий отказ и не скрытая замена старого элемента
новым.

## MVP (реалистично — часы) vs Full (реалистично — дни)

### MVP — «Доска = коллекция референсов»

Что юзер получает: несколько именованных досок, переключение между ними,
активная доска реально влияет на генерацию — её фото уходят в модель как
референсы вместе с промтом выбранного стиля. Это уже настоящая
персонализация («мой стиль» = мои фото, всегда под рукой), просто без
автоматического текстового описания.

**Почему быстро**: ничего не требует новой AI-инфраструктуры.
- Хранение досок (список, название, фото-URL, какая активна) — **на
  стороне вебаппа, в localStorage устройства**. Осознанное упрощение v1: не
  синхронизируется между устройствами, теряется при очистке данных браузера
  — это ограничение явно проговорено, апгрейд на серверное хранилище (D1,
  инфраструктура уже поднята для Студии) — отдельная будущая задача, не
  меняющая UX выше.
- Загрузка фото в доску — **переиспользует уже готовую и задеплоенную**
  Cloudflare Function-заливку на imgbb (та же, что фронтенд построил для
  референсов Студии нейромультиков) — фронтенду не нужно писать новый
  аплоадер.
- Единственная новая штука на стороне бота — распознать новый payload-экшен
  (условно `board_refs`/`br`, массив уже захостенных URL картинок) и
  загрузить их в `state.references`, ровно тем же кодом, что уже обрабатывает
  ручную загрузку фото юзером (SirNike.py:3596-3599) — не новый пайплайн, а
  переиспользование существующего.

### Full — «Доска сама описывает свой стиль и подмешивает его всегда»

Что добавляется сверх MVP: после того как юзер собрал доску, кнопка
«✨ Понять мой стиль» запускает vision-анализ фото доски (обобщение уже
работающего в проде `extract_style_description_from_reference` — не «фото
причёски», а «фото всей доски» → 2-4 предложения: цветовая гамма,
настроение, композиция). Результат — редактируемый текст, который юзер
видит и может поправить (принцип: человеческий контроль, не чёрный ящик):

```
Что подметил ИИ (можно поправить):
[текстовое поле, предзаполнено сгенерированным описанием]
```

Пока доска активна, это описание **автоматически** уходит в промт КАЖДОГО
выбранного стиля — это и есть настоящая «персонализация» из запроса
блогера. Баннер активности в этом режиме отличается текстом, чтобы юзер
понимал разницу в поведении:

```
🖼️ Доска активна — стиль ИИ подмешивается в каждую генерацию
```

**Почему дольше**: требует нового кросс-репо решения (вебапп статичен, ключ
vision-вызова живёт только у бота).
- Нужен новый способ доставки текста описания в промт при КАЖДОМ применении
  стиля — не разово, как в MVP. Кандидат: отдельное поле в payload
  (например `board_note`/`bn`, ОТДЕЛЬНОЕ от уже существующего `note`/`n`,
  которое несёт «свои пожелания» юзера по конкретному стилю) — их нельзя
  схлопывать в одну строку молча, иначе бот потеряет уже отлаженную логику
  приоритета `apply_user_note_override` (юзер-текст должен побеждать
  дефолтное описание стиля, `docs/specs/2026-07-17_note_override_weak.md`).
  Итоговый алгоритм совмещения (доска-описание как базовый слой + стиль +
  «свои пожелания» юзера поверх) — решение бэкенда, не дизайна; спека
  фиксирует ТРЕБОВАНИЕ (оба текста должны доехать и не затирать друг
  друга), не реализацию.
- Сам vision-вызов анализа доски — по образцу уже проверенного в проде
  `extract_style_description_from_reference`, но нужен отдельный промт для
  модели («опиши общий стиль/настроение/палитру ПОДБОРКИ фото», не «причёску
  одного человека») и тестирование на реальных досках — судя по прошлому
  опыту с похожей задачей (усиление «своих пожеланий», см. спеку выше),
  сила формулировки почти всегда требует минимум одной живой итерации
  после первого теста, не попадает с первого раза.
- Хранение текста описания надёжнее делать не только в localStorage
  (текст важно не терять) — тут уже осмысленно перейти на серверное
  хранилище (D1) для самой доски, а не только для фото.

**Рекомендация по архитектуре Full (для бэкенда, не блокирует UX-спеку)**:
анализ — синхронный vision-вызов (секунды, как уже работает
`extract_style_description_from_reference`), НЕ полноценная асинхронная
job-очередь по образцу Студии нейромультиков (там очередь оправдана
видео-генерацией на 20+ минут — здесь несоразмерно). Достаточно: вебапп
шлёт фото доски боту обычным payload'ом с новым экшеном, бот в течение
секунд отвечает текстом описания в чат и одновременно кладёт его в свою
SQLite, привязав к id доски (тот же UUID, что вебапп уже сгенерировал
локально) — последующие применения стиля с этой доски слать `board_id`
вместо всего текста заново (короче, надёжнее лимита Telegram payload).
Финальное решение — за бэкенд-сессией, здесь только предложение.

## Сверка: «Вкладка со стилем» — уже есть, пробелов нет

Библиотека стилей в вебаппе (категории, поиск, избранное, входы и
инлайн-кнопкой, и reply-клавиатурой) закрывает этот пункт Midjourney по
факту уже сегодня — отдельного экрана проектировать не нужно. Единственный
реальный пробел — недостающая секция «Топ-стили» (данные уже собираются
ботом, `get_template_usage_counts`, но не доставлены в вебапп — P2, уже в
очереди `docs/briefs/frontend.md`, ТЗ готово:
`docs/specs/2026-07-16_top_styles_stats_feed.md`). Рекомендация: поднять её
приоритет и выпустить ОДНОВРЕМЕННО с досками — вместе они делают каталог
ощутимо более «живым» для демонстрации блогеру (два новых раздела на
главном экране вместо одного), при этом «Топ-стили» технически не связаны с
досками и не блокируют их.

---

## Принципы продукта — как соблюдены

- Одна кнопка = одно предсказуемое действие: «Сделать доску активной»
  всегда значит одно и то же независимо от того, была ли активна другая
  доска — просто заменяет активную, с явным подтверждением в чате, не
  тихой подменой.
- Кнопка навигации никогда не удаляет данные: «‹ Мои доски», «Отключить» —
  ничего не стирают. Удаление фото/доски — отдельные явные действия
  (крестик на фото, «Удалить доску» в меню «⋮» с подтверждением).
- Тексты инструкций называют кнопки ровно как подписаны — сверено выше по
  каждому экрану.
- Меню не спамить: одна новая секция в каталоге, не новый пункт в главном
  меню бота.
- Без слов «промт»/«референс»/«модель» в пользовательских текстах — везде
  «фото» и «стиль».

## Критерий приёмки

### MVP
- Юзер создаёт доску, называет её, добавляет 3-8 фото, делает активной —
  весь путь без ошибок и зависаний.
- Баннер активной доски виден на ВСЕХ экранах каталога (главная,
  категория, поиск), не только на главной.
- Переключение на другую доску / «Отключить» — мгновенно, без
  рассинхрона между баннером и реальным состоянием.
- «Сделать активной и продолжить» → бот в чате подтверждает подключение и
  число загруженных референсов → выбор ЛЮБОГО стиля из библиотеки →
  генерация использует и промт стиля, и фото доски одновременно, юзеру не
  нужно повторно грузить фото.
- Лимиты (5 досок, 10 фото в доске, 8 — в референс одной генерации)
  соблюдены, сообщения о достижении лимита понятны.
- Юзер, не создавший ни одной доски, не видит изменений в привычном
  флоу применения стиля (кроме одной новой строки на главной каталога).

### Full (дополнительно к MVP)
- После сборки доски юзер жмёт «✨ Понять мой стиль» → получает
  редактируемое текстовое описание в разумное время (секунды, не минуты).
- Пока доска активна, это описание автоматически участвует в КАЖДОЙ
  генерации выбранного стиля — заметно на результате (визуальная проверка
  на живых тестах, не только по факту, что текст «доехал»).
- Собственные «свои пожелания» юзера по конкретному стилю (`input_hint`)
  по-прежнему работают и не перезаписываются описанием доски молча —
  оба текста доезжают, порядок приоритета явный и предсказуемый.
- Текст описания доски переживает переоткрытие вебаппа (не теряется при
  обычном использовании — минимальная надёжность хранения).
