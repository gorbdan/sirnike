# ТЗ: Доски — Full («доска сама описывает свой стиль»)

Дата: 2026-08-09. Приоритет: **P0** (продолжение партнёрской интеграции с
блогером — MVP уже в проде, это следующий шаг того же запроса). Расширяет
[docs/specs/2026-08-09_mood_boards.md](2026-08-09_mood_boards.md) (раздел
«Full», строки 247-304) — та версия описывала цель и оставляла архитектуру
на усмотрение бэкенда. Этот файл — уже принятое, доведённое до
реализуемости решение по открытым вопросам оттуда.

Автор — фронтенд-сессия (webapp-часть реализована и проверена live в этом
же заходе, см. коммит в репо вебаппа). Контракт ниже согласован с тем, что
уже реально отправляет вебапп — переносить его без изменений.

## Что нового по сравнению с MVP

MVP: доска = разовый набор фото-референсов, `board_refs` грузится в
`state.references` ОДИН раз и живёт до следующей генерации (как обычная
ручная загрузка фото) — я проверила код: `state.references`/`style_extract`
уже сегодня one-shot везде (сбрасываются после `run_generation`,
`state.style_extract = False  # one-shot — не переносить`, SirNike.py:4972,
и во всех местах, где `state.references = []` стоит явным сбросом). Это
значит **Full нельзя построить поверх `state.references`** — она физически
не переживает вторую генерацию. Нужно отдельное персистентное поле.

## 1. Новое действие в payload (вебапп → бот)

Webapp уже шлёт (реализовано и задеплоено на моей стороне, ветка `main`
репо вебаппа):

```json
{
  "action": "board_style_analyze",
  "board_id": "<локальный UUID доски, тот же, что в localStorage вебаппа>",
  "title": "<имя доски>",
  "board_refs": ["<url1>", "..."]
}
```

- Короткий алиас действия: `bsa` (как у остальных экшенов — `a` для `action`).
- `board_refs` — ДО 10 фото (весь состав доски, не срез до 8 — Full смотрит
  на всю подборку, MVP-потолок в 8 относится только к референсам ГЕНЕРАЦИИ,
  не к анализу).
- Кнопка в вебаппе показывается от 2 фото в доске (меньше — недостаточно
  для «стиля подборки», текст-заглушка вебапп решает сам).
- Payload шлётся ТЕМ ЖЕ каналом и с той же защитой от инлайн-входа, что и
  `board_refs` (см. `docs/BOT_CONTRACT.md`, раздел «Доски») — `tg.sendData`,
  доступно только когда библиотека открыта с reply-клавиатуры; вебапп уже
  честно предупреждает и не закрывается, если вход инлайн.

## 2. Новый обработчик на боте

Симметрично `apply_webapp_board_refs_payload` — новая функция (условно
`apply_webapp_board_style_analyze_payload`), диспетчер в
`apply_webapp_prompt_payload_v2` добавляет ветку `action in {"board_style_analyze", "bsa"}`.

Шаги:
1. Взять до 6 URL из `board_refs` (не все 10 — латентность и стоимость
   vision-вызова растут с числом картинок, 6 достаточно для «палитра/
   настроение/композиция»; если бэкенд решит иначе — не блокер, отметить в
   RELEASE_NOTES фактическое число).
2. Новая функция vision-анализа **по образцу** уже проверенного в проде
   `extract_style_description_from_reference` (SirNike.py:4599) — тот же
   Zveno text-only vision вызов, НО:
   - принимает список URL, не один;
   - другой промт модели — не «причёска и макияж одного человека», а
     «опиши общий визуальный стиль ПОДБОРКИ фото: цветовая гамма,
     настроение, композиция/освещение — 2-4 предложения, без упоминания
     лиц/личности людей на фото» (важно сохранить формулировку «без лиц» —
     та же причина, что в оригинальной функции: описание уходит в промт
     генерации, лишнее упоминание внешности конкретного человека там не
     нужно и вредно).
   - возвращает `Optional[str]`, `None` при ошибке — вызывающий код должен
     ответить юзеру человеческим текстом об ошибке, НЕ оставлять доску в
     подвешенном состоянии (см. критерий приёмки).
3. Ответ юзеру в чат (текст фиксирован, менять только по смыслу
   ошибки-транслитерации, не переформулировать):

   ```
   🖼️ Доска «Вечерний гламур» — вот что подметил ИИ:

   «<результат vision-вызова, 2-4 предложения>»

   Это описание будет подмешиваться в промт КАЖДОЙ генерации, пока доска
   активна.
   ```
   Кнопки под сообщением (`InlineKeyboardMarkup`, 2 в ряд):
   `✅ Всё верно` (`callback_data=bsc_<board_id_short>` — подтвердить как
   есть) · `✏️ Поправить` (`callback_data=bse_<board_id_short>` — просит
   юзера прислать свой текст следующим сообщением, тем же паттерном ввода
   свободного текста, что уже есть у `input_hint`/«свои пожелания»).

   `board_id` — UUID вебаппа (36 символов) не влезет в 64-байтный
   `callback_data` вместе с префиксом с запасом — резать по образцу
   `pl_usen_` (см. `docs/specs/2026-07-17_inline_note_passthrough.md`):
   либо укоротить до первых ~20 символов UUID (достаточно уникально в
   пределах одного юзера, у которого максимум 5 досок), либо — чище —
   хранить соответствие `short_id → board_id` в `state` на время диалога
   (действует только для ЭТОГО чата, ttl не нужен — перезапишется при
   следующем анализе). Выбор реализации — на бэкенд.

4. При нажатии `✅ Всё верно` или после присланного юзером исправленного
   текста: **сохранить** `state.board_style_note = <текст>` и
   `state.board_style_board_id = <board_id>` — новые поля `UserState`
   (SirNike.py:431), НЕ переиспользовать `references`/`style_extract`.
   Персистентность в БД для `UserState` — сверить с тем, как уже хранятся
   остальные долгоживущие поля состояния (если `UserState` не пишется в
   SQLite между рестартами бота — не блокер для v1, вебапп и так теряет
   доски при очистке браузера, симметричное ограничение проговорено в
   исходной спеке; если пишется — сохранить туда же, ALTER TABLE-совместимо,
   см. `DB_GUIDE.md`).
5. Бот подтверждает: `✅ Стиль доски подключён — активен для следующих
   генераций.`

## 3. Применение при генерации (КАЖДАЯ, не одна)

В месте, где сегодня уже применяется `apply_user_note_override(prompt, user_note)`
(SirNike.py:4051, 6363 — «свои пожелания» юзера к конкретному стилю) —
добавить ПЕРЕД этим шагом наложение `state.board_style_note`, если оно
заполнено:

```
итоговый промт = board_style_note (базовый слой, если есть)
                → + промт выбранного стиля
                → apply_user_note_override(..., user_note)  (свои пожелания — поверх, как сегодня)
```

Порядок принципиален (уже зафиксирован в исходной спеке, раздел Full,
строки 275-279): «свои пожелания» юзера должны побеждать/дополнять описание
доски, а не наоборот — если алгоритм совмещения текстов сложнее конкатенации
(с учётом, что `apply_user_note_override` уже имеет свою логику приоритета,
`docs/specs/2026-07-17_note_override_weak.md`), решение за бэкендом, но
ТРЕБОВАНИЕ (оба текста доезжают, порядок предсказуем, ничего не молча
теряется) — часть критерия приёмки.

`state.board_style_note` НЕ сбрасывается после одной генерации (в отличие
от `references`/`style_extract`) — специально проверить, что общий
код завершения генерации, который чистит `state.references = []` в
разных местах, НЕ трогает новое поле по ошибке (сейчас это два разных
поля, но легко случайно добавить сброс «по аналогии» — не делать).

## 4. Отключение стиля доски (важно — раньше этого механизма не было)

MVP-кнопка «Отключить» в баннере вебаппа — **остаётся как есть**, чисто
косметическая (прячет баннер, чистит `references`, бот про неё не узнаёт —
это не меняется, потому что она про одноразовые референсы). Для
персистентного `board_style_note` этого недостаточно — нужен способ явно
выключить именно его, и он не может жить в вебаппе (закрытие мини-аппа при
каждом переключении — плохой UX для частого действия).

Решение: отключение — **чат-нативное**, кнопка живёт у бота, не в вебаппе:
- Добавить пункт в существующее меню применения стиля/референсов бота
  (или отдельная команда/кнопка — на усмотрение бэкенда, здесь фиксируется
  только ТРЕБОВАНИЕ) — «🖼️ Отключить стиль доски», доступная, пока
  `state.board_style_note` заполнено. Например: инлайн-кнопка остаётся
  ПОД сообщением-подтверждением из п.2 навсегда (Telegram позволяет
  нажимать инлайн-кнопки под старыми сообщениями сколько угодно) —
  `callback_data=bsoff_<short_id>` очищает оба поля и отвечает
  `✅ Стиль доски отключён — дальше генерации идут без него.`
- Активация ДРУГОЙ доски (обычный `board_refs` ИЛИ новый
  `board_style_analyze`) должна сама заменить/очистить предыдущий
  `board_style_note` — «одна активная доска одновременно», уже
  зафиксировано в MVP-спеке (раздел «Лимиты»), для Full действует
  так же.

## 5. Ошибки — не оставлять «зависшую» доску

Если vision-вызов вернул `None` (нет ключа, таймаут, пустой ответ) —
сообщить юзеру человеческим текстом (`Не получилось разобрать стиль
доски — попробуй ещё раз чуть позже.`), НЕ ставить `board_style_note` в
пустую строку и НЕ активировать доску молча без стиля (юзер должен явно
понимать: анализ не удался, а не «доска подключилась, но без AI-текста»).
Не откатываться тихо на MVP-поведение (`board_refs`) — это другой контракт,
юзер жал другую кнопку.

## 6. Что НЕ входит в этот заход (сознательно)

- Хранение `board_style_note` в D1/на стороне вебаппа для отображения
  текста внутри самого мини-аппа (мокап исходной спеки показывал
  редактируемое поле ПРЯМО в экране доски вебаппа) — технически
  недостижимо без нового постоянного HTTP-моста вебапп↔бот (у бота сейчас
  нет публичного HTTP-сервера, только исходящие `aiohttp`-клиентские
  вызовы — проверено `grep` по SirNike.py). Редактирование текста
  переносится в чат бота (см. п.2, кнопка «✏️ Поправить») — это
  сознательное архитектурное отклонение от исходного мокапа, не забытая
  часть.
- Синхронный ответ в вебапп до его закрытия — та же причина.

## Критерий приёмки

- Юзер с доской ≥2 фото жмёт «✨ Понять мой стиль» в вебаппе → в чате
  бота за секунды (не минуты) приходит описание + кнопки «Всё верно»/
  «Поправить».
- После подтверждения — описание участвует в промте КАЖДОЙ следующей
  генерации любого стиля из библиотеки, не только первой (проверить минимум
  на 2 подряд разных стилях).
- «Свои пожелания» (`input_hint`) к конкретному стилю по-прежнему доезжают
  и не теряются молча рядом с описанием доски.
- Явная кнопка отключения стиля доски у бота работает и подтверждается
  текстом.
- Переключение на другую доску (`board_refs` или `board_style_analyze`)
  автоматически снимает предыдущий `board_style_note` — не наложение двух
  досок одновременно.
- Ошибка vision-вызова — понятное сообщение, доска НЕ помечается стилизованной.
- `py_compile` + `pytest tests/` зелёные, новый блок тестов на
  `board_style_analyze`/подтверждение/отключение (по образцу
  `tests/test_block_20_midjourney.py` — один файл на блок функциональности).
