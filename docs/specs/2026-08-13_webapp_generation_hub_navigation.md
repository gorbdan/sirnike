# Спека: Хаб генерации — Full (единая навигация + Midjourney/Аватар-конструкторы)

Дата: 2026-08-13. Продолжает [docs/specs/2026-08-13_webapp_generation_hub.md](2026-08-13_webapp_generation_hub.md)
(раздел «Full», строки ~270-352 исходного файла — там были только скетчи).
Этот файл — доведённое до реализуемости решение, **тот же уровень
детализации, что [docs/specs/2026-08-09_mood_boards_full.md](2026-08-09_mood_boards_full.md)**
(образец, на который прямо сослалась Аня). Исходный файл со скоупом MVP
(видео-конструктор) **не трогаю и не переписываю** — MVP уже в разработке.

## Важная находка перед началом: бэкенд уже ушёл дальше исходного MVP-скоупа

Пока я читала контекст, обнаружила, что бэкенд-сессия уже реализовала БОЛЬШЕ,
чем формально входило в MVP — эта спека написана с опорой на РЕАЛЬНЫЙ код,
не только на текст исходной спеки:

- `apply_webapp_generation_payload` (SirNike.py:4146) уже диспетчерит по
  `product` на ТРИ функции: `_apply_webapp_generation_video` (4169),
  `_apply_webapp_generation_midjourney` (4280), `_apply_webapp_generation_avatar`
  (4338) — то есть бэкендная обработка payload `start_generation`/`sg` для
  Midjourney и Аватара **уже написана и рабочая**, за своими kill-switch'ами
  `MIDJOURNEY_CONSTRUCTOR_ENABLED`/`AVATAR_CONSTRUCTOR_ENABLED` (config.py:243-244,
  оба `0` по умолчанию).
- Карточки подтверждения для Midjourney/Аватара в чате уже реализованы
  дословно (см. «Midjourney-конструктор» и «Аватар-конструктор» ниже — тексты
  зафиксированы КАК ЕСТЬ в коде, не придуманы заново).
- `video_constructor_kb(user_id)` (SirNike.py:4137) — рабочий паттерн
  «инлайн-кнопка `web_app=WebAppInfo(url=get_prompt_webapp_url(user_id) +
  "&tab=video_constructor")`» уже используется дважды: при входе
  `MENU_BTN_VIDEO` (3257) и при нажатии «✏️ Изменить»/«🔁 Начать заново»
  после карточки подтверждения (4269-4275, сейчас без префилла).

**Чего нет** — и это ровно то, что закрывает эта спека:
1. Ни один вход в Midjourney (`_cb_menu_midjourney`, callback `menu_midjourney`)
   и Аватар (`MENU_BTN_AVATAR`, `avatar_actions_kb` → `avatar_gen_refsheet`) не
   ведёт в вебапп-конструктор — оба всё ещё открывают чат-флоу
   (текстовый промт / выбор типа кнопками).
2. Единой навигации (таб-бар «Создать/Стили/Доски/Студия») в вебаппе нет —
   есть три независимых входа с разными query-параметрами (`tab=studio`,
   `tab=video_constructor`, без параметра = каталог/Библиотека).
3. Кнопка после карточки подтверждения называется «🔁 Начать заново» и
   ведёт на ПУСТОЙ конструктор (`&tab=video_constructor` без данных) —
   ровно то ограничение, которое MVP-спека сознательно узаконила и оставила
   на Full (раздел «✏️ Изменить» ниже).
4. `_video_constructor_cfg_payload()` (SirNike.py:1270) отдаёт конфиг
   ТОЛЬКО для видео-моделей — у Midjourney/Аватара сейчас нет канала
   получить актуальную цену без похода в чат.

## 1. Единая навигация

### 1.1 Таб-бар

Ровно как зафиксировано в исходной спеке (не меняю формулировку):

```
[ Создать ]   Стили   Доски   Студия
```

Порядок фиксирован (слева направо, «Создать» — первый и активный по
умолчанию). Иконки-подсказки (эмодзи перед подписью таба, тот же язык, что
уже используют кнопки бота — не выдумываю новый набор):

| Таб | Подпись | Иконка | Откуда взята (не новая) |
|---|---|---|---|
| 1 | Создать | ✨ | `MENU_BTN_PHOTO = "✨ Сгенерировать фото"` (SirNike.py:1509) |
| 2 | Стили | 📚 | `MENU_BTN_LIBRARY = "📚 Библиотека стилей"` (1513) |
| 3 | Доски | 🖼️ | иконка баннера доски, уже используется в мокапе `2026-08-09_mood_boards_mockup.html` и в тексте «🖼️ Доска «…» активна» |
| 4 | Студия | 🎬 | `"🎬 Студия мультиков"` (1496) |

**Реализация — не с нуля.** У вебаппа уже есть физический `.tab-bar`-компонент
(добавлен под Студию, `docs/briefs/frontend.md`: «новый таб «Студия» —
`.tab-bar` было жёстко на 3 колонки — поправлено»), значит он уже умеет
переменное число колонок. Full **переиспользует этот же компонент**, не
строит навигацию заново — расширяет набор вкладок до 4 и меняет то, что
сегодня открывается по умолчанию (см. 1.4).

### 1.2 Клиентский роутинг — без нового payload

Переключение между табами — **чисто клиентское состояние** (JS-переменная
активного экрана + перерисовка, как уже работает переключение
категорий/поиска внутри сегодняшней Библиотеки). Никакого `tg.sendData()`
при простом тапе по табу. `tg.initData`/`initDataUnsafe` не трогаются, сеть
не дёргается (кроме уже существующих: синк `prompt_library.json` при
открытии, загрузка фото в аплоадер imgbb по явному тапу «+ добавить фото»).

Единственный сетевой/навигационный триггер — открытие Mini App САМО
(бот передаёт весь нужный контекст в URL один раз при старте, см. раздел 6
про `prefill` и уже работающий `cfg`/`price_table`). Всё дальше — SPA-рендер
внутри одной открытой сессии.

### 1.3 Экран «Создать» — сетка продуктов

```
Создать

[ 🖼 Фото ]  [ 🎬 Видео для Reels ]
[ 🪄 Аватар ]  [ 🎨 Midjourney ]
```

Порядок и состав — ровно 4 плитки, как в постановке задачи. Тап по каждой:

| Плитка | Куда ведёт | Почему именно так |
|---|---|---|
| 🖼 Фото | Переключает на таб **«Стили»** (не отдельный экран) | В этом продукте фото-генерация ЦЕЛИКОМ идёт через выбор стиля из библиотеки — отдельного «Фото-конструктора» никогда не проектировалось и не нужно (тот же вывод, что в `2026-08-09_mood_boards.md`, раздел «Сверка»: «вкладка со стилем уже есть — Библиотека»). Свободный текстовый ввод промта («✨ Сгенерировать фото», `MENU_BTN_PHOTO`, callback `generate`) — отдельный, НЕ трогаемый чат-флоу для тех, кто уже знает, что хочет; в сетку «Создать» не выносится (тот же принцип, что уже применён к «Улучшить фото» — 2-таповый флоу, переносить нечего выгадывать). |
| 🎬 Видео для Reels | Открывает Конструктор видео (Экран V1 из MVP-спеки) | Без изменений в самом экране — только новая точка входа (клиентский переход внутри Mini App вместо повторного открытия через query-параметр). |
| 🪄 Аватар | Открывает Аватар-конструктор (раздел 3) | — |
| 🎨 Midjourney | Открывает Midjourney-конструктор (раздел 2) | — |

Плитка **скрывается**, если продукт выключен фичефлагом на момент сборки
`cfg` (см. раздел 5) — `midjourney.enabled=false`/видео без ни одной
активной модели/`avatar.enabled=false` — тот же принцип, что уже действует
для инлайн-кнопок в чате (`MIDJOURNEY_ENABLED` скрывает «🎨 Midjourney 🆕» в
`photo_menu_kb`, SirNike.py:1475).

### 1.4 Что открывается по умолчанию — важная миграция

Сегодня `get_prompt_webapp_url(user_id)` **без** `&tab=...` открывает
каталог Библиотеки (это неявный дефолт вебаппа). Full делает дефолтом
**«Создать»**. Это не косметика — 12 существующих мест в SirNike.py зовут
`get_prompt_webapp_url(...)` без явного `tab` (строки 922, 1433, 1537, 1588,
1696, 1705, 2099, 2217, 2409, 4054, 4535, 6710, 7000 — полный список,
проверено `grep`), и как минимум два из них — кнопки, буквально
называющиеся «📚 Открыть библиотеку» (1696, 1705, `webapp_open_kb`). Если
дефолт вебаппа молча сменится на «Создать», эти кнопки станут врать о своём
эффекте (нарушение принципа продукта: «тексты инструкций называют кнопки
ровно как подписаны»).

**Требование к бэкенду**: при переходе на Full КАЖДЫЙ существующий вызов
`get_prompt_webapp_url(...)`, который сегодня НЕ передаёт `tab`, должен
получить явный `&tab=library` (не полагаться на новый дефолт). Дефолт
«Создать» действует только там, где параметр `tab` физически отсутствует —
то есть фактически только для НОВЫХ входов, которые эта спека добавляет
(например, обновлённый `webapp_open_kb`, если решите сознательно сделать его
входом в «Создать» — тогда это отдельное осознанное решение продукта, не
побочный эффект миграции).

### 1.5 «Стили» — без изменений в каталоге, кроме одного удаления

Сам каталог (категории/поиск/карточка стиля) — без изменений. Меняется одна
вещь: горизонтальная секция «🖼️ Мои доски» (сегодня на главной каталога,
`2026-08-09_mood_boards.md`, «Экран 1») **убирается** с этого экрана —
дублирует новый таб «Доски» (раздел 1.6). Правило «одна кнопка/секция — один
путь» (не плодить два одинаковых входа в одну и ту же функцию) важнее, чем
экономия одного тапа. Остаётся: закреплённый баннер активной доски
(«🖼️ Доска «…» активна · [Сменить] · [Отключить]») — он не заменяет вход
в управление досками, а информирует о текущем состоянии, поэтому остаётся
на «Стили» **и** появляется на «Создать» (см. 1.7).

### 1.6 «Доски» — управление досками как полноценный таб

Контент таба — ровно то, что сегодня было секцией «Мои доски» плюс сам
Экран 2 (`2026-08-09_mood_boards.md`) при тапе по конкретной доске:
список плиток досок (или пустое состояние «+ Новая доска» — «Собери фото для
своего стиля»), тап по плитке → просмотр/редактирование конкретной доски
(сетка фото, «✅ Сделать активной», «✨ Понять мой стиль»). Ничего в самих
экранах Досок не меняется — меняется только их адрес: не подраздел
Библиотеки, а первый уровень навигации. `board_refs`/`board_style_analyze`
payload — без изменений (`docs/BOT_CONTRACT.md`, разделы «Доски»/«Доски —
Full»).

### 1.7 Баннер активной доски на «Создать»

```
🖼️ Доска «Вечерний гламур» активна — фото пойдут в референс
```

Показывается под шапкой экрана «Создать» (не перекрывает сетку продуктов),
той же логикой видимости, что и баннер на «Стили» — читает то же клиентское
состояние (`localStorage`, доски целиком живут на стороне вебаппа, бот их не
хранит — не меняется). Тап по баннеру → переключает на таб «Доски» (тот же
принцип, что «Сменить» на баннере каталога сегодня).

## 2. Midjourney-конструктор

### 2.1 Экран (уточнённый относительно черновика исходной спеки)

```
🎨 Midjourney

Опиши, что хочешь сгенерировать
[ текстовое многострочное поле, до 6 строк видимых, дальше скролл внутри поля
  placeholder: «Например: девушка в кафе, утренний свет, плёночная фотография» ]
Осталось N символов                     ← появляется только при приближении к лимиту (см. 2.3)

Фото-референс (необязательно)
[ + добавить фото ]  /  [ фото ✕ ]     ← ОДНО фото, не «до 9» как у видео (см. 2.2)

Стоимость: 15 🍇 за сетку из 4 вариантов
Увеличение понравившегося — отдельно, 10 🍇

[     🚀 Продолжить в чат     ]
```

Цифры `15`/`10` — НЕ хардкод в вебаппе, приходят через `cfg` (раздел 5,
`cfg.midjourney.grid_cost`/`upscale_cost`), сегодня это
`MIDJOURNEY_GRID_COST`/`MIDJOURNEY_UPSCALE_COST` (config.py:279-280, дефолты
15/10 — реальные текущие значения на момент написания спеки).

Кнопка «🚀 Продолжить в чат» активна только при непустом тексте — дословно
та же проверка, что уже стоит в бэкенде: `_cb_mj_generate`
(SirNike.py:6510) и уже написанный `_apply_webapp_generation_midjourney`
(4317-4321) оба отклоняют пустое описание с одинаковым по смыслу текстом
«Нужно описание…» — вебапп не должен даже давать тапнуть, но бэкенд
подстрахован независимо (устаревший кэш вебаппа не пробьёт эту защиту).

### 2.2 Почему ровно 1 фото, не 9

`_apply_webapp_generation_midjourney` (SirNike.py:4305-4315) уже написана и
берёт **только первый** URL из массива `refs`, с явным комментарием в коде:
«EvoLink Midjourney принимает ровно один референс — URL подставляется в
НАЧАЛО строки prompt, не отдельное поле». Вебапп-экран должен визуально
отражать это ограничение — аплоадер Midjourney-конструктора **разрешает
только 1 фото** (не «до 9», как в видео-конструкторе), при попытке добавить
второе — замена первого с тостом «Midjourney использует одно фото-референс,
заменил» (не тихая потеря второго фото и не ошибка — предсказуемое
поведение, юзер сразу видит результат замены).

### 2.3 Лимит длины описания

Midjourney-промт не ограничен по смыслу продукта коротким текстом (в отличие
от `note`/«свои пожелания», который жёстко режется до ~30 байт для
callback_data в инлайн-1-тапе — другая сущность, не путать). Ограничение —
только техническое, от `tg.sendData()` (~4096 байт на весь payload). Вебапп
считает то же самое, что уже считает Конструктор видео для поля описания
(тот же паттерн «осталось N символов», см. `BOT_CONTRACT.md` правило для
`set_prompt`: «обрезка на стороне вебаппа с явным предупреждением в UI поля,
не молчаливая отправка урезанного текста»). Практический бюджет для
Midjourney даже комфортнее видео — нет 9 URL фото-референсов в том же
payload (максимум 1), так что весь запас уходит под текст.

### 2.4 Карточка подтверждения в чате (уже реализована, текст дословно)

```
🎨 Готово к запуску

Описание: {description}
Фото-референс: приложен ✅            ← строка есть, только если референс приложен
Стоимость: 15 изюминок за сетку из 4 вариантов
(увеличение понравившегося — отдельно, 10 изюминок)
```

Кнопка: `🚀 Сгенерировать` (`callback_data="mj_generate"` — существующий
коллбэк `_cb_mj_generate`, ничего нового не пишется в биллинге). Источник —
`_apply_webapp_generation_midjourney` (SirNike.py:4323-4334), текст выше
скопирован из кода буква в букву, не придуман заново.

### 2.5 Точка входа из чата — что меняется

Сегодня единственный вход — инлайн-кнопка «🎨 Midjourney 🆕»
(`photo_menu_kb`, callback `menu_midjourney`) → `_cb_menu_midjourney`
(SirNike.py:6485) сразу переводит юзера в режим ожидания текстового
сообщения (`state.waiting_for_mj_prompt = True`) с текстом-инструкцией
«Опиши, что хочешь сгенерировать, одним текстовым сообщением».

**Full**: если `MIDJOURNEY_CONSTRUCTOR_ENABLED and PROMPT_WEBAPP_URL` —
`_cb_menu_midjourney` вместо перевода в режим ожидания текста отправляет
сообщение с инлайн-кнопкой открытия конструктора (новый хелпер
`midjourney_constructor_kb(user_id)`, зеркало уже существующего
`video_constructor_kb`):

```python
def midjourney_constructor_kb(user_id: int) -> InlineKeyboardMarkup:
    return InlineKeyboardMarkup([[
        InlineKeyboardButton(
            "🎨 Открыть конструктор",
            web_app=WebAppInfo(url=get_prompt_webapp_url(user_id) + "&tab=midjourney_constructor"),
        ),
    ]])
```

Сопроводительный текст — по аналогии с видео (SirNike.py:3258-3263):

```
🎨 Midjourney

Опиши, что хочешь сгенерировать, и приложи фото-референс (по желанию) —
в конструкторе. Возвращайся сюда за запуском.
```

Если флаг выключен — поведение НЕ меняется (текущий текстовый мини-флоу),
кнопка на конструктор просто не появляется. Это единственная точка входа в
Midjourney сегодня (нет отдельной reply-кнопки на постоянной клавиатуре,
`MENU_BTN_*` не включает Midjourney) — значит обновить нужно только этот
один хендлер, в отличие от видео, где входа было два.

## 3. Аватар-конструктор

### 3.1 Экран

```
🪄 Аватар

Какой тип?
[ 👩 Женский ]  [ 👨 Мужской ]  [ 🧒 Детский ]

Фото (3–8, чем больше — тем точнее)
[ + добавить фото ]  [ фото1 ✕ ] [ фото2 ✕ ] ...

Стоимость: 5 🍇

[     🚀 Продолжить в чат     ]
```

- Тип выбран по умолчанию — «👩 Женский» (тот же дефолт, что уже в бэкенде:
  `_apply_webapp_generation_avatar` откатывает пустой/некорректный
  `avatar_type` на `"female"`, SirNike.py:4360-4362).
- Фото — до `MAX_AVATAR_PHOTOS = 8` (SirNike.py:438, существующая
  константа, тот же потолок, что и у ручной загрузки в чат). Подсказка
  «3–8» — не жёсткий минимум на кнопке (кнопка активна и от 1 фото, дальше
  описано), а рекомендация по качеству результата — тот же текст смысла,
  что уже в чат-версии: «Пришли 3–8 своих фото» (MENU_BTN_AVATAR,
  SirNike.py:3301).
- Кнопка «🚀 Продолжить в чат» активна от **1** фото (не от 3) — бэкенд уже
  требует ровно это: `_apply_webapp_generation_avatar` (4371-4375)
  отклоняет только полностью пустой список `avatar_photos`, «3+» — это
  рекомендация в подписи поля, не хардкод-гейт кнопки (тот же принцип, что
  уже действует для видео: «кнопка есть ⇔ действие сейчас возможно», не
  «действие оптимально»).
- Цена `5 🍇` — из `cfg.avatar.cost` (раздел 5), сегодня это
  `BASE_GENERATION_COST` (аватар тарифицируется как обычная фото-генерация,
  `_cb_avatar_gen_start`, SirNike.py:6125: `avatar_cost = BASE_GENERATION_COST`).

### 3.2 Карточка подтверждения в чате (уже реализована, текст дословно)

```
🪄 Готово к запуску

Тип: женский 👩
Фото: 4 шт.
```

Кнопка: `🚀 Сгенерировать аватар (4 фото)` — число подставляется динамически
(`callback_data="avatar_gen_start"`, существующий коллбэк, без изменений в
биллинге/генерации). Источник — `_apply_webapp_generation_avatar`
(SirNike.py:4377-4388), `avatar_kind_label` (1607-1613) даёт варианты
`"женский 👩"`/`"мужской 👨"`/`"детский 🧒"` — текст выше взят из кода 1-в-1.

### 3.3 Точка входа из чата — что меняется

Сегодня два шага: MENU_BTN_AVATAR/`avatar_actions` → `avatar_actions_kb`
(экран управления существующими аватарами) → кнопка «🪄 Создать / заменить
аватар» либо «🪄 Сгенерировать аватар» (`callback_data="avatar_gen_refsheet"`)
→ `_cb_avatar_gen_refsheet` (SirNike.py:6049) → чат просит фото → после фото
показывает `avatar_gen_kind_kb()` (тип: 👩/👨/🧒) → `_cb_avatar_gen_start`.

**Full не трогает `avatar_actions_kb`** (экран со списком уже загруженных
аватаров/переключением активного — самостоятельная, отдельная от
генерации функция, вне скоупа конструктора). Меняется только то, что
происходит по тапу «🪄 Создать / заменить аватар» /
«🪄 Сгенерировать аватар»: если `AVATAR_CONSTRUCTOR_ENABLED and
PROMPT_WEBAPP_URL` — вместо перевода в режим ожидания фото
(`_cb_avatar_gen_refsheet`) показывается инлайн-кнопка конструктора (новый
хелпер `avatar_constructor_kb(user_id)`, тот же паттерн):

```python
def avatar_constructor_kb(user_id: int) -> InlineKeyboardMarkup:
    return InlineKeyboardMarkup([[
        InlineKeyboardButton(
            "🪄 Открыть конструктор",
            web_app=WebAppInfo(url=get_prompt_webapp_url(user_id) + "&tab=avatar_constructor"),
        ),
    ]])
```

Сопроводительный текст:

```
🪄 Аватар

Выбери тип и загрузи фото в конструкторе — и возвращайся сюда за запуском.
```

Флаг выключен → поведение не меняется (текущий чат-флоу с
`avatar_gen_kind_kb`/ожиданием фото).

## 4. Интеграция Библиотеки

### 4.1 Видео-стиль: «Использовать» больше не шлёт payload сразу

Сегодня (не в скоупе MVP, но меняется в Full): тап «🚀 Использовать» на
видео-стиле (item с `"type": "video"` в `prompt_library.json`) шлёт
`set_video_prompt`/`set_video_prompt_ref` payload немедленно — бот получает
готовый промт и открывает старую чат-панель `video_kb`.

**Стало**: тап «🚀 Использовать» на видео-стиле **не закрывает Mini App и
не шлёт payload** — клиентским переходом переключает вебапп на таб
«Создать» → сразу открывает Конструктор видео (Экран V1) с уже
заполненным полем «Что должно происходить в видео» (текст = `prompt`
выбранного стиля, тот же, что раньше уходил в payload напрямую). Юзер
донастраивает модель/формат/качество/длительность/фото поверх подставленного
описания и жмёт «🚀 Продолжить в чат» — вот тут уходит ОДИН payload
`start_generation`, несущий уже финальный `description` (текст стиля +
возможные правки юзера, слитые в одно поле — конструктор не различает
«текст от стиля» и «текст, который дописал юзер», это одно текстовое поле
с курсором в конце после автоподстановки, юзер может редактировать
свободно).

Почему так, а не по-старому: сама цель Full — свести ЛЮБОЙ путь входа в
видео-генерацию к одному конструктору с одной карточкой подтверждения,
вместо двух параллельных путей (старая чат-панель для стилей, новый
конструктор — для прямого входа). Оставлять два флоу одновременно —
удвоенная поверхность багов и путаница «почему из библиотеки видео выглядит
иначе, чем из «Создать»».

Фото-стили (без `"type": "video"`) — **без изменений**: «Использовать»
работает как сегодня (мгновенный payload `set_prompt`/`set_prompt_ref`,
закрытие Mini App, чат просит фото). У фото-генерации нет конструктора и не
появляется в этой спеке (см. 1.3 — «Фото» ведёт в «Стили», не создаёт новый
экран).

### 4.2 `cat_idx`/`item_idx` при переходе через библиотеку

Правило резолва не меняется: индексы передаются и резолвятся ботом
(«не доверяем присланному тексту»), но здесь они используются НЕ как раньше
(мгновенный payload → бот резолвит на своей стороне), а как основа для
клиентской подстановки текста В САМОМ ВЕБАППЕ — вебапп резолвит `prompt`
локально из уже загруженного `prompt_library.json` (source of truth,
синкается с ботом отдельно) для отображения в поле конструктора. Финальный
payload `start_generation` при отправке всё равно несёт **готовый текст**
(`description`/`p`), не `ci`/`ii` — потому что к моменту отправки текст уже
мог быть отредактирован юзером в конструкторе, индексы библиотеки больше не
описывают точно то, что уходит. `ci`/`ii` в контракте `start_generation`
(раздел 7) остаются опциональными и информационными (для статистики «стиль
пришёл из библиотеки Х» на стороне бота, если решите её вести) — НЕ
источником резолва текста, в отличие от `set_video_prompt_ref`.

### 4.3 Совместимость с баннером активной доски

Если у юзера активна доска — баннер виден на «Стили» (как сегодня) и теперь
дополнительно на «Создать» (раздел 1.7). Переход «Использовать» видео-стиль
→ Конструктор видео **не трогает** состояние доски: фото доски по-прежнему
подмешиваются на стороне бота при финальной сборке `refs` в payload —
вебапп-конструктор при сборке итогового массива `refs` **мёрджит** фото,
явно загруженные в конструкторе, с фото активной доски (тот же принцип, что
уже зафиксирован в исходной MVP-спеке, раздел «Новый контракт payload»:
«вебапп мёрджит их в один массив ДО отправки — бот получает уже готовый
список, не два разных источника»). Информационная строка «🖼️ С доски «…»
тоже подмешается» (сегодня — в карточке фото-стиля) добавляется и в
Конструктор видео рядом с блоком «Фото», если доска активна.

## 5. Живой прайс без дублирования логики (расширение на Midjourney/Аватар)

### 5.1 Почему это ПРОЩЕ, чем у видео

У видео цена зависит от модели × качества × длительности — формула
(`calc_seedance_cost`) уже сериализуется в вебапп через таблицу `prices` в
`cfg.video_models[]` (`_video_constructor_cfg_payload`, SirNike.py:1270-1310,
уже реализовано в MVP). У Midjourney и Аватара цена — **фиксированное целое
число**, не формула: `MIDJOURNEY_GRID_COST`/`MIDJOURNEY_UPSCALE_COST`
(config.py:279-280) и `BASE_GENERATION_COST` соответственно. Вебаппу не
нужно ничего «пересчитывать» — только отобразить готовое число, которое
бот положил в `cfg`.

### 5.2 Расширение `cfg` (не новый параметр URL — тот же `cfg=`)

`_video_constructor_cfg_payload()` (SirNike.py:1270) сегодня возвращает
`{"video_models": [...]}`. Full расширяет ЭТУ ЖЕ функцию (переименовать в
`_generation_hub_cfg_payload()`, если хочется точности имени — не
обязательно, поведение важнее имени) двумя новыми ключами:

```json
{
  "video_models": [ /* без изменений, как сегодня */ ],
  "midjourney": {
    "enabled": true,
    "grid_cost": 15,
    "upscale_cost": 10
  },
  "avatar": {
    "enabled": true,
    "cost": 5,
    "types": ["female", "male", "child"]
  }
}
```

- `midjourney.enabled`/`avatar.enabled` — источник для скрытия плиток на
  экране «Создать» (раздел 1.3), читаются из `MIDJOURNEY_CONSTRUCTOR_ENABLED`
  И `MIDJOURNEY_ENABLED` одновременно (конструктор бессмысленно показывать,
  если сам продукт Midjourney выключен целиком) и `AVATAR_CONSTRUCTOR_ENABLED`
  соответственно.
- `midjourney.grid_cost`/`upscale_cost` — прямое зеркало
  `MIDJOURNEY_GRID_COST`/`MIDJOURNEY_UPSCALE_COST`, без дублирования (те же
  переменные, не копия значений вручную).
- `avatar.cost` — зеркало `BASE_GENERATION_COST`.
- `avatar.types` — статический список (не меняется рантаймом), нужен
  вебаппу только для порядка отрисовки кнопок типа — не обязателен
  (конструктор может зашить порядок 👩/👨/🧒 у себя), но включён для
  единообразия с видео (где список моделей уже приходит с бэкенда, а не
  хардкодится в вебаппе).

### 5.3 Правило не меняется

Финальная цена в карточке подтверждения в чате **всегда** пересчитывается
бэкендом на момент показа — для Midjourney/Аватара это тривиально (константы
читаются напрямую в `_apply_webapp_generation_midjourney`/`_avatar`, не из
payload), но принцип формулируется явно и здесь: даже для фиксированной
цены источник истины — бот, вебапп только отображает то, что ему прислали.

## 6. «✏️ Изменить» с сохранением черновика

### 6.1 Что меняется относительно MVP

MVP сознательно назвала кнопку после карточки подтверждения «🔁 Начать
заново» и вела на ПУСТОЙ конструктор — инфраструктуры предзаполнения не
было. Она уже реализована как `web_app=WebAppInfo(url=get_prompt_webapp_url(user_id)
+ "&tab=video_constructor")` (SirNike.py:4271-4274, кнопка стоит второй в
клавиатуре карточки подтверждения видео, рядом с «🚀 Запустить видео»).

**Full**: та же кнопка, то же место в клавиатуре, **новый текст и новое
поведение**:

```python
InlineKeyboardButton(
    "✏️ Изменить",
    web_app=WebAppInfo(url=get_prompt_webapp_url(user_id) + "&tab=video_constructor&prefill=" + prefill_b64),
)
```

Аналогично добавляется в клавиатуры подтверждения Midjourney и Аватара
(сегодня там всего одна кнопка запуска — Full добавляет вторую, «✏️
Изменить», тем же паттерном, `&tab=midjourney_constructor&prefill=.../
&tab=avatar_constructor&prefill=...`).

### 6.2 Архитектура сериализации — почему именно так

У бота нет публичного HTTP-входа (только polling, `python-telegram-bot`) —
единственный канал бот→вебапп — URL, который бот САМ формирует в момент
рендера кнопки. Это то же ограничение, что уже явно задокументировано и
принято в `2026-08-09_mood_boards_full.md` («Что НЕ входит»: «недостижимо
без нового постоянного HTTP-моста вебапп↔бот»). Решение зеркалит уже
принятый в исходной MVP-спеке набросок (раздел «✏️ Изменить», строки
325-336) — здесь он доводится до конкретного алгоритма:

1. К моменту рендера карточки подтверждения `UserState` УЖЕ содержит все
   разобранные поля (`video_model`, `video_aspect_ratio`, `video_mode`,
   `video_duration`, `video_face_grid`, `video_prompt`, `refs`-эквивалент
   через `get_video_image_urls(state)` — код уже это делает для запуска
   генерации, ничего нового собирать не нужно).
2. Новая функция `build_generation_prefill(state, product) -> str` (пустая
   строка при ошибке сериализации — деградация в «кнопка ведёт на пустой
   конструктор», не падение) строит JSON **теми же короткими алиасами**, что
   уже определены в контракте `start_generation` (раздел 7) — `pr`, `vm`,
   `ar`, `q`, `d`, `fg`, `p`, `r`, `at` — и кодирует `base64.urlsafe_b64encode`,
   без padding (`=` можно обрезать и восстанавливать по длине — тот же
   трюк, что уже используется для `note_b64` в инлайн-1-тапе,
   `2026-07-17_inline_note_passthrough.md`).
3. **Одно намеренное отличие от входящего контракта**: `prefill` НЕ несёт
   `ci`/`ii` — на исходящей стороне бот является источником истины и кладёт
   в `p` уже полностью резолвленный текст (`state.video_prompt`/`mj_prompt`),
   а не индексы для повторного резолва. Индексы имеют смысл только как
   защита от недоверия К ВХОДЯЩИМ данным от вебаппа — на исходящей стороне
   бот доверяет сам себе.
4. Вебапп при открытии с параметром `prefill` декодирует base64 → JSON →
   заполняет поля Конструктора нужного таба ДО первой отрисовки (не мигает
   пустым экраном, который через кадр заполняется — важно для ощущения
   «мои настройки на месте», не для перфекционизма ради перфекционизма).
   Если `prefill` отсутствует или не парсится — конструктор открывается
   пустым (штатное поведение, не ошибка).

### 6.3 Фото-референсы в `prefill` — это URL, не байты

`refs`/`r` в `prefill` — **те же уже захостенные на imgbb HTTPS-URL**, что
хранятся в `UserState` (`get_video_image_urls(state)` уже возвращает готовые
URL, не `__img_xxx__` in-memory-рефы — те живут только до момента запуска
генерации и резолвятся в реальные байты отдельно; для «Изменить» это не
нужно, конструктору для превью фото хватает публичного URL, как и обычному
аплоадеру Досок/Студии). Никакой передачи байт через URL не требуется и не
предлагается — это было бы физически невозможно в разумных пределах размера
URL.

Единственный риск: если исходные фото были загружены НЕ через imgbb
(например, юзер прислал их в чат заново поверх конструктора, что технически
не предусмотрено в MVP-флоу — фото всегда идут через вебапп-аплоадер) —
такого случая в текущей архитектуре нет, `refs` в `UserState` для этого
продукта заполняются только из payload вебаппа, значит всегда уже URL.

### 6.4 Проблема размера URL — решение, не констатация

`get_prompt_webapp_url` сегодня уже ведёт бюджет: история генераций (`&h=`)
обрезается под лимит `budget = 2048 - len(url) - len("&h=")` (SirNike.py:1334).
Добавление `prefill` поверх существующих `rev`/`cfg`/`balance`/`h` рискует
раздуть URL сверх разумного (хотя официального жёсткого лимита на
`web_app`-URL в Bot API, в отличие от `sendData` 4096 байт, нет — на
практике очень длинные URL ненадёжны в WebView разных платформ, и проект
уже держится консервативных бюджетов везде, где возможно — не повод стать
первым местом, где эта дисциплина нарушается). Решение — деградация по
приоритету полей, а не «либо всё, либо ничего»:

1. **Первым делом `prefill` вытесняет `h` (историю)** — при рендере кнопки
   «✏️ Изменить»/аналогов бот строит URL БЕЗ `&h=` вовсе (история
   генераций не нужна и не отображается на экране Конструктора — это поле
   имеет смысл только на экране каталога/Библиотеки). Это освобождает
   заметный кусок бюджета почти всегда.
2. **`prefill` использует те же короткие алиасы**, что и исходящий payload
   (`pr`/`vm`/`ar`/`q`/`d`/`fg`/`p`/`r`/`at`) — уже компактный формат, ничего
   нового придумывать не нужно.
3. **`description`/`p` в prefill не может быть больше, чем было в исходном
   входящем payload** — раз юзер уже когда-то ОТПРАВИЛ этот текст боту
   через `sendData`, он уже прошёл клиентскую обрезку под лимит 4096 байт
   всего payload (правило `BOT_CONTRACT.md` для `set_prompt`) — значит
   верхняя граница `p` в prefill УЖЕ ограничена этим прошлым событием, не
   нужен отдельный повторный контроль.
4. **Если после сборки всего URL (rev+cfg+balance+prefill, без h) длина
   превышает `WEBAPP_URL_SAFE_BUDGET` (новая константа, предложение — 3500
   байт, тот же порядок величины, что уже используется как консервативный
   потолок в проекте для `sendData`, см. `2026-07-12_webapp_payload.md`:
   «порог 3500 байт») — бот дропает `refs`/`r` из prefill ПОСЛЕДНИМ (не
   первым и не единственным полем) и добавляет к тексту сопровождающего
   сообщения одну строку: «Настройки восстановлены — фото придётся добавить
   заново» (не молчаливая потеря, юзер явно предупреждён). Модель/формат/
   качество/длительность/описание всё равно долетают — это подавляющее
   большинство ценности «Изменить» (typing текста — самое дорогое по
   времени действие, которое жалко терять; фото добавить заново — секунды).
   На практике это крайний случай: `cfg` для видео (самый тяжёлый продукт
   по числу моделей) в текущей конфигурации (7 моделей с ценами) — не
   больше нескольких сотен байт в base64, `prefill` без `refs` — тоже
   несколько сотен байт максимум (текст описания редко достигает
   практического потолка `sendData`). Реальные превышения бюджета ожидаются
   крайне редко, но правило деградации фиксируется как явное поведение, не
   как «доработаем, если случится».
5. Midjourney/Аватар — `prefill` для них заведомо меньше видео (нет
   моделей/формата/качества/длительности, `refs` — максимум 1 URL у
   Midjourney, до 8 у Аватара) — угроза бюджета для этих двух продуктов
   практически отсутствует, п.4 для них — чисто защитный код на будущее,
   не ожидаемый сценарий.

## 7. Полный контракт payload — расширение (не новое действие)

Действие остаётся `start_generation`/`sg` (уже определено в MVP-спеке,
раздел «Новый контракт payload», уже реализовано бэкендом для трёх
продуктов). Full добавляет то, что MVP оставила «опционально описанным», но
не свела в одну таблицу — фиксирую здесь полный актуальный список полей,
сверенный с РЕАЛЬНЫМ кодом (`_apply_webapp_generation_video/midjourney/avatar`):

| Поле | Кратко | Продукт | Значение |
|---|---|---|---|
| `action` | `a` | все | `start_generation` (алиас `sg`) |
| `product` | `pr` | все | `video` \| `midjourney` \| `avatar` — обязателен |
| `video_model` | `vm` | video | как в MVP-спеке, без изменений |
| `aspect` | `ar` | video | как в MVP-спеке |
| `quality` | `q` | video | как в MVP-спеке |
| `duration` | `d` | video | как в MVP-спеке |
| `face_grid` | `fg` | video | как в MVP-спеке |
| `description` | `p` | video, midjourney | видео-описание ИЛИ Midjourney-текст (общее поле — один и тот же алиас для обоих продуктов, диспетчер уже читает `payload.get("description") or payload.get("p")` в обеих функциях) |
| `refs` | `r` | video, midjourney, avatar | video: до 9 URL (мердж вручную загруженных + доски). midjourney: используется только `refs[0]` (см. 2.2), остальные молча игнорируются — не баг. avatar: до `MAX_AVATAR_PHOTOS=8` (`state.avatar_photos = refs[:MAX_AVATAR_PHOTOS]`, SirNike.py:4369) |
| `avatar_type` | `at` | avatar | `female` \| `male` \| `child`, дефолт `female` при отсутствии/некорректном значении |
| `cat_idx`/`item_idx` | `ci`/`ii` | video (опц.) | информационные, НЕ используются для резолва текста в `start_generation` (в отличие от `set_video_prompt_ref`) — см. 4.2. Бэкенду сегодня НЕ нужно их читать в `_apply_webapp_generation_video` для функциональности; если понадобится статистика происхождения — можно добавить логирование без изменения контракта. |
| `board_id` | `bi` | video (опц.) | как в MVP-спеке — информационное поле |

Правила (без изменений относительно MVP, подтверждаю действующими и для
Full):
- `product` обязателен, валидируется против фичефлагов НА СТОРОНЕ БОТА —
  уже реализовано (`_apply_webapp_generation_video` откатывает на
  `seedance2` с предупреждением при недоступной модели, midjourney/avatar-
  ветки честно отвечают «Эта функция сейчас недоступна» при выключенном
  конструкторе — SirNike.py:4177-4184, 4288-4292, 4346-4350).
- `refs` — бот берёт свой потолок сам (9/1/8 по продукту), вебапп может
  визуально ограничивать раньше (Midjourney-аплоадер разрешает только 1
  фото, раздел 2.2), но бэкенд НЕ полагается на клиентское ограничение —
  берёт срез сам, как и раньше.

## 8. Что нужно от бэкенда (Full) — актуальный список

Часть уже сделана — отмечено явно, чтобы не дублировать работу:

1. ✅ **Готово**: `apply_webapp_generation_payload` с диспетчером на 3
   продукта, независимые kill-switch'и `MIDJOURNEY_CONSTRUCTOR_ENABLED`/

   Аватара — тексты зафиксированы в разделах 2.4/3.2 этой спеки как

2. **Новое**: `midjourney_constructor_kb`/`avatar_constructor_kb` (раздел
   2.5/3.3) + обновление `_cb_menu_midjourney` и хендлера кнопки
   `avatar_gen_refsheet` — единственные точки входа для этих двух
   продуктов, по одной на каждый (в отличие от видео, где их было две).
3. **Новое**: расширение `_video_constructor_cfg_payload()` (или
   переименование) полями `midjourney`/`avatar` (раздел 5.2) — единый `cfg`
   параметр обслуживает все три продукта.
4. **Новое**: `build_generation_prefill(state, product)` + подстановка
   `&prefill=` в кнопку «✏️ Изменить» на всех трёх карточках подтверждения
   (раздел 6) — переименование кнопки с «🔁 Начать заново» на «✏️ Изменить»
   для видео (текст меняется ТОЛЬКО вместе с реализацией десериализации на
   стороне вебаппа — до тех пор кнопка обязана оставаться «🔁 Начать
   заново», иначе нарушается принцип «текст кнопки не обещает того, чего
   нет физически», прямо как зафиксировано в MVP-спеке).
5. **Новое**: миграция всех вызовов `get_prompt_webapp_url(...)` без явного
   `tab=` на `&tab=library` (раздел 1.4, полный список из 12 мест) — иначе
   смена дефолта Mini App на «Создать» тихо ломает существующие кнопки

6. **Новое**: `WEBAPP_URL_SAFE_BUDGET`-логика деградации (раздел 6.4,
   п.4) — не блокирует базовый кейс, но должна быть реализована до вывода

   ошибку открытия Mini App вместо контролируемой деградации).
7. Единая навигация (таб-бар, экран «Создать», перенос «Мои доски» в
   отдельный таб) — **целиком на стороне вебаппа**, бэкенду для этого
   ничего дополнительно передавать не нужно сверх уже расширенного `cfg`
   (продукты/цены/доступность) — сам роутинг клиентский (раздел 1.2).

## Принципы продукта — как соблюдены (Full)

- Одна кнопка = одно предсказуемое действие: «✏️ Изменить» переименовывается
  ТОЛЬКО когда реально восстанавливает данные — до тех пор остаётся «🔁
  Начать заново», текст не обгоняет реализацию.
- Кнопка навигации не удаляет данные: переключение табов «Создать/Стили/
  Доски/Студия» — чисто клиентский рендер, ничего не сбрасывает (черновик
  Конструктора при уходе на другой таб и возврате обратно — сохранённое
  клиентское состояние вебаппа, не обнуляется просто фактом смены вкладки).
- Тексты инструкций называют кнопки ровно как подписаны: все новые кнопки
  («🎨 Открыть конструктор», «🪄 Открыть конструктор») копируют паттерн уже
  проверенной «🎬 Открыть конструктор».
- Меню не спамить: Midjourney/Аватар получают ОДНУ новую точку входа каждый
  (заменяют существующую, не добавляют вторую параллельно), персистентная
  reply-клавиатура бота не меняется — ни один новый `MENU_BTN_*` не
  добавляется.
- Без слов «промт»/«референс»/«модель» как абстрактных терминов — «Опиши,
  что хочешь сгенерировать», «Фото-референс» намеренно НЕ используется как
  подпись поля (заменено на «Фото» с уточнением в скобках, где нужно; слово
  «референс» в этой спеке встречается только в технических разделах для
  бэкенда/фронтенда, не в пользовательских текстах экрана).

## Критерий приёмки (Full)

- Таб-бар «Создать/Стили/Доски/Студия» открывается по умолчанию на
  «Создать», переключение между табами не создаёт новых сетевых запросов
  и не закрывает Mini App.
- Плитка «Фото» на «Создать» ведёт на «Стили» (не на пустой экран и не в
  чат); «Видео для Reels»/«Аватар»/«Midjourney» открывают свои конструкторы.
- Плитки скрыты для продуктов, выключенных фичефлагом на момент открытия
  Mini App (сверено с `cfg`).
- Тап «Использовать» на видео-стиле в Библиотеке НЕ закрывает Mini App —
  переключает на «Создать → Видео» с уже заполненным описанием, юзер может
  донастроить остальные поля и запустить — ОДИН payload на выходе, не два.
- Midjourney- и Аватар-конструкторы проходят тот же путь, что видео: один
  экран → одна карточка подтверждения (тексты сверены с разделами 2.4/3.2
  дословно) → существующая кнопка запуска (`mj_generate`/
  `avatar_gen_start`) без изменений в биллинге.
- «✏️ Изменить» реально восстанавливает модель/формат/качество/
  длительность/детектор лиц/текст описания/тип аватара — не пустой экран;
  фото восстанавливаются, если не сработала деградация по бюджету URL (в
  этом случае — явное предупреждение в тексте, не молчание).
- Существующие кнопки «Открыть библиотеку» (12 точек входа, раздел 1.4)
  по-прежнему открывают каталог, не экран «Создать» — регрессия по
  умолчанию Mini App не случилась.
- Живой прайс в Midjourney-/Аватар-конструкторе совпадает с ценой в
  финальной карточке подтверждения бота (обе стороны читают одни и те же
  константы через `cfg`, расхождение — баг).
- Баннер активной доски виден на «Создать» и «Стили» одновременно, «Мои
  доски»-секция больше не дублируется на «Стили» — только на «Доски».
- `MIDJOURNEY_CONSTRUCTOR_ENABLED=false`/`AVATAR_CONSTRUCTOR_ENABLED=false`
  мгновенно возвращают сегодняшние чат-флоу для соответствующего продукта,
  независимо друг от друга и от `VIDEO_CONSTRUCTOR_ENABLED`.
