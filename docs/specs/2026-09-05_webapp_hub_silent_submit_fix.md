# Спека: Хаб «Создать» молчит на пустых обязательных полях + доска хоронит ввод юзера

Дата: 2026-09-05. По находкам живого теста «от лица растерянного новичка»
поверх уже собранного Хаба генерации ([docs/specs/2026-08-13_webapp_generation_hub.md](2026-08-13_webapp_generation_hub.md),
[..._navigation_full.md](2026-08-13_webapp_generation_hub_navigation_full.md),
[..._menu_simplification...](2026-08-14_menu_simplification_and_enhance_constructor.md)).
Разбор находок: [audits/2026-09-05_full_naive_az_test.txt](../../audits/2026-09-05_full_naive_az_test.txt).
Все 4 пункта — правки в репо вебаппа (Cloudflare Pages), не в боте.

## Почему сейчас

Спека [2026-08-14](2026-08-14_menu_simplification_and_enhance_constructor.md)
уже требовала «кнопка неактивна без фото» для конструктора enhance (п. 52
той спеки) — то есть принцип «кнопка есть ⇔ действие сейчас возможно» уже
заявлен как требование ко всему хабу. Живой тест показал, что на проде
это НЕ так ни для одного из 5 конструкторов: кнопка визуально активна
(яркая, кликабельна), но при пустом обязательном поле клик по ней просто
ничего не делает. Это не новая фича — это регресс/недоделанная реализация
уже принятого требования, и чинить нужно снаружи (клиентская валидация),
а не только полагаться на бэкенд-фолбэк.

## Часть 1 — P0: «Продолжить в чат» не должна молчать на пустом вводе

### Репро (проверено на всех пяти конструкторах прода)

| Конструктор | Пустое поле | Результат клика |
|---|---|---|
| Фото | описание пустое, фото не приложено | тишина |
| Аватар | ни одного фото | тишина |
| Midjourney | описание пустое | тишина |
| Улучшить фото | фото не приложено | тишина |
| Видео для Reels | фото-референс не приложен (модель требует фото) | тишина |

Во всех случаях: попап не закрывается, в чат не приходит ни одного
сообщения от бота. Проверено: бэкенд ГОТОВ ответить по-человечески на
пустой payload — например, `_apply_webapp_generation_avatar` (SirNike.py:
4982–5038) при пустых `avatar_photos` шлёт `"Нужно хотя бы одно фото —
вернись в конструктор и добавь фото для аватара."` (5016–5020), и
аналогичные фолбэки есть у остальных product-веток диспетчера
`apply_webapp_generation_payload`. Но это сообщение НИКОГДА не приходит
на проде — значит, `Telegram.WebApp.sendData()` (или его эквивалент)
на клиенте, по всей видимости, вообще не вызывается при пустых полях.
Для контраста: карточки библиотеки («Стили» → карточка → «Использовать»)
всегда доставляют данные боту исправно — проблема локальна для кнопки
«Продолжить в чат» конструкторов хаба, не общий сбой доставки.

### Требование

1. **Клиентская валидация ДО отправки.** Для каждого из 5 конструкторов
   определить обязательные поля:
   - Фото: описание ИЛИ хотя бы одно фото (как минимум одно из двух —
     соответствует тексту-подсказке «Без фото используем твой сохранённый
     аватар — если он есть», но описание пустое и фото нет = нечего
     генерировать).
   - Видео для Reels: описание ИЛИ фото-референс — как минимум одно,
     кроме моделей, которым фото обязательно (Seedance-семейство,
     см. существующую бэкенд-проверку `if selected_model in
     {"seedance2", "seedance2_fast"} and len(video_images) < 1` —
     продублировать то же условие на клиенте).
   - Аватар: хотя бы 1 фото.
   - Midjourney: описание не пусто.
   - Улучшить фото: хотя бы 1 фото.
2. При невалидном состоянии — кнопка «🚀 Продолжить в чат» либо визуально
   неактивна (серая, disabled — как уже требовала спека 2026-08-14 для
   enhance), либо активна, но клик показывает ИНЛАЙН-ошибку РЯДОМ с
   недостающим полем («Добавь описание или фото», «Нужно хотя бы одно
   фото для аватара» и т.п.) — не системный алерт, короткая подсказка в
   стиле остальных подсказок экрана. На выбор фронтенда, какой вариант
   реализовать — критерий приёмки одинаков для обоих (см. ниже).
3. **Страховка на бэкенд-фолбэк не убирать.** Даже после клиентской
   валидации оставить существующие бэкендовые проверки пустого payload —
   это защита от races/багов клиента, а не дублирование работы.

### Критерий готовности

- На всех 5 конструкторах: пустое обязательное поле → клик по «Продолжить
  в чат» НИКОГДА не приводит к молчанию — либо кнопка недоступна для
  клика, либо юзер сразу видит, что не так.
- Заполненные поля → поведение не меняется (сегодня работает исправно).
- Живой тест после фикса: повторить все 5 сценариев из таблицы выше,
  каждый должен дать понятную реакцию, а не тишину.

## Часть 2 — P1: подтверждение хаба хоронит ввод юзера под текстом доски

### Репро

Хаб-подтверждение (сообщение «✨ Готово к запуску», отправляется после
успешного `sendData` из конструктора «Фото» при активной доске) содержит
ПОЛНОСТЬЮ развёрнутый английский текст анализа доски (5+ строк:
`"Overall visual style/mood baseline from the user's mood board (apply
as a background aesthetic layer under everything else — palette,
atmosphere, composition): ..."`), и только ПОСЛЕ него, последней
строкой — реальный ввод юзера. Формально текст юзера не обрезан (в
отличие от бага в чат-флоу бота, см. отдельный бриф бэкенду), но
практически нечитаем: обычный человек не станет вычитывать абзац
английского текста, чтобы найти своё «кот на пляже» на восьмой строке.

### Требование

Карточка подтверждения хаба должна показывать ТОЛЬКО пользовательский
ввод (описание, которое юзер реально напечатал в текстовом поле
конструктора) — без склейки с текстом анализа доски. Факт «доска
подмешана к этой генерации» — отдельная короткая строка-индикатор
(например, «🖼 Доска подмешана в промт», как уже сделано в
`photo_draft_text` на стороне бота), а не встраивание текста доски в
само описание, которое видит юзер. Технически: если склейка «текст доски
+ ввод юзера» происходит на клиенте перед отправкой в payload — либо
отправлять оба поля раздельно (описание юзера отдельным полем,
флаг/факт применения доски — отдельным), либо, если склейка неизбежна
по контракту payload, хотя бы в ТЕКСТЕ ПОДТВЕРЖДЕНИЯ показывать только
хвост после разделителя. Согласовать конкретный контракт с бэкендом
перед реализацией (может измениться payload `product=photo`).

### Критерий готовности

Подтверждение хаба при активной доске показывает описание = то, что
юзер реально напечатал, плюс отдельную строку «доска подмешана» — без
английского текста анализа доски в самом описании.

## Часть 3 — P2: экран «Доски» не показывает активную доску

На списке досок и внутри карточки конкретной доски нет визуального
признака «эта доска сейчас подключена к генерациям». Кнопки «✨ Понять
мой стиль» / «✅ Подключить фото без анализа» выглядят одинаково
для активной и неактивной доски.

### Требование

Добавить явный статус-бейдж (например, «Активна ✅» / «Подключена») на
карточке доски, которая сейчас применяется к генерациям (соответствует
`state.board_style_note` на бэкенде — нужен способ прочитать этот статус
с клиента, например через уже существующий баланс-эндпоинт вебаппа или
отдельное поле в конфиге хаба; согласовать с бэкендом).

### Критерий готовности

Открыв «Доски», юзер сразу видит, какая доска (если есть) сейчас активна,
без необходимости идти в чат бота и смотреть на карточку черновика.

## Часть 4 — P2: мёртвый клик по существующему аватару

На экране «Аватар» клик по одному из трёх готовых превью (женский/
мужской/детский) не производит никакого эффекта — не открывает просмотр
в полный размер, не переключает активный тип.

### Требование

Либо сделать клик по превью действием (открыть просмотр фото ИЛИ
переключить активный тип для следующей генерации — на усмотрение
фронтенда, что логичнее по UX), либо, если клик не должен ничего делать,
убрать курсор-указатель/hover-состояние, чтобы не выглядело кликабельным.

### Критерий готовности

Клик по превью аватара либо делает что-то осмысленное, либо превью визуально
не выглядит интерактивным.
